# عقود التراكيب وحدود التوسع

المرحلة2 صاغت العقود؛ المرحلة4 نفذت وصفات C01/C02/C03 على الفرع للمراجعة، 2026-11-12. **D01 يبقى PROPOSED / NOT IMPLEMENTED**.

C01/C02/C03 وصفات HTML/CSS موجودة الآن، بحالة Draft للمراجعة، دون API JavaScript أو عائلات جديدة. مصادرها والتحميل والاستهلاك الفعلي في [دليل التراكيب](COMPOSITIONS.md). لا تغيير في توكنز الهوية أو نضج العائلات14 والمتغيرات6 القائمة. [واجهات المصدر الحالية](COMPONENT-API-CONTRACTS.md) منفصلة عن سياسات مستهلك الأمثلة. موضع العمل الوحيد مستودع UX؛ لا إصلاح Micro أو اختبار داخله كشرط قبول.

## قاعدة البناء والملكية

التراكيب الثلاثة وصفات عامة تستهلك المصدر المشترك، لا شاشات Showcase ولا نسخ CSS لكل شاشة. قبل إضافة abstraction نثبت سياقين مستقلين يحتاجان التشريح نفسه؛ إن كفى markup موثق لا نضيف JS. نربط كل تعديل لاحقًا بمالك واحد داخل العائلة المناسبة أو مصدر تركيب مشترك واضح. اختيار موضع الملف النهائي بعد تدقيق المرحلة3؛ لا ننقل ملف previews كما هو دون مراجعة.

كل خانة أدناه وصف دلالي لا API إطار عمل. أسماء CSS المنفذة موثقة في دليل التراكيب؛ التواقيع في قسم D01 فقط ما زالت مقترحة غير منفذة. للمستهلك بياناته ونصوصه ومعنى الأفعال والتحقق التجاري؛ للمكتبة القراءة والتخطيط والحالات الدلالية والموارد التي تُنشئها. القيم المعروضة أرقام فعلية؛ النسبة فقط لحصة/تقدم لهما مقام ومعنى معلنان.

## C01 — قراءة قيمة بسياق — وصفة منفذة للمراجعة

**الأساس:** Info Card/Info Strip الحالي، وOrganization للحالة والإجراء. لا إنشاء بطاقة رقم ثانية تنافس الموجود.

| الخانة | العقد |
|---|---|
| تسمية | مطلوبة وواضحة؛ لا اعتماد على أيقونة وحدها. |
| القيمة والوحدة | قيمة عرض يقدمها المستهلك، والوحدة ظاهرة عند الحاجة. صفر يختلف عن مفقود؛ المفقود له وصف صريح ولا يتحول إلى0. |
| السياق | فترة أو مصدر أو نطاق اختياري؛ مطلوب عندما لا يُفهم الرقم بدونه. |
| الحالة/المؤهل | تسمية ونبرة معتمدتان، وعلامة provisional/estimated مثلًا فقط إذا قدمها المصدر؛ لا استنتاج من علامة الرقم أو لونه. |
| الملاحظة | توضيح قصير اختياري لا ينافس الرقم؛ لا إخفاء معلومة أساسية فيه. |
| الإجراء/المصدر | رابط أو زر مستقل ذو اسم وهدف واحد؛ غيابه لا يجعل البطاقة تفاعلية. |

**التحديث:** مصدر واحد للقيمة والسياق والحالة. لا parser أو حساب جمع/رصيد/نسبة/تقريب داخل التركيب. لا تبديل وحدة أو فترة بصمت. isolate للجزء الرقمي فقط، والوحدة العربية خارج جزيرة LTR؛ لا قلب الإشارة أو قص الخانات الطويلة. التحميل حالة يصرح بها المستهلك؛ إن ظهرت قراءة سابقة تميز بصراحة عن الجديدة.

**الشكل:** basic/compact الافتراضي حسب السياق، وfeatured اختيار ذو سبب، لا مربع ضخم لكل قراءة. الالتفاف قبل قص القيم؛ لا ارتفاع ثابت يخفي الملاحظة. توزيع أكثر من قراءة لا يوحي بجمع وحدات غير متجانسة.

**معايير القبول:** سياقان عامان بقيمة/وحدة/فترة مختلفتين، صفر ومفقود وقيمة طويلة وموقعة، حالة/مؤهل وإجراء غائب/حاضر، انتظار/خطأ دون نسبة مختلقة،360 RTL وعدم قص أو فيض. لا أحداث تغيير تجاري للقراءة الساكنة، وتنظيف الأطفال حسب API كل عائلة.

## C02 — صف وقائمة تشغيلية كثيفة — وصفة منفذة للمراجعة

**الأساس:** Organization `.m-row` وامتداد المصدر `components/organization/operational-row.css`. ثبتت الوصفة في سياقي الاستلام والمواد؛ الأمثلة تستهلك المصدر مباشرة. مسار CSS القديم باقٍ كمدخل معاينة يستورد المصدر؛ composition-row كان صنف معاينة خاصًا وليس API إنتاجية. لا تنسيق خاص منسوخ لكل موضع.

| الخانة | العقد |
|---|---|
| الاسم والوصف | اسم أساسي ووصف اختياري، يعرضان كامل المعنى دون حجم ثابت. |
| القيمة والوحدة | قراءة اختيارية مستقلة عن الاسم؛ الصفر/المفقود/الإشارة كما في C01. |
| الحالة/التاريخ | نص قابل للفهم مع نبرة اختيارية؛ لا تاريخ أو حالة مشتقان دون مصدر. |
| الأفعال | صفر أو فعل رئيسي وأفعال ثانوية لازمة فقط؛ أسماء صريحة وأهداف مستقلة. |
| الإفصاح | اختياري بمشغّل واحد وaria-expanded/controls؛ الأفعال داخله لا تفعّل الصف مرة ثانية. |

**السيمانتيكس:** قائمة فعلية عند تعدد السجلات. صف أحادي الوجهة يمكن أن يكون رابطًا؛ الصف متعدد الأفعال حاوية مع رابط وأزرار أشقاء، بلا زر داخل رابط أو تداخل أهداف. العرض الساكن لا يتظاهر بأنه زر. لا action-on-row-click مخفي ينافس أزرارًا داخله.

**الضيق:** القراءة أولًا، ثم التفاف الحالة والإجراء عند الحاجة؛ لا تصغير خط أو قص مبلغ أو ضغط الأهداف تحت48px حيث ينطبق العقد. لا فرض ارتفاع موحد بين صفين مختلفي المحتوى. ترتيب القراءة والتركيز منطقي في RTL وLTR. المقصود كثافة مفيدة، لا وضع كل معلومة في صف واحد.

**الحالات:** فراغ القائمة حالة Messages أو نص معلن مع فعل اختياري، ليس صفًا وهميًا بقيمة0. خطأ/انتظار على مستوى القائمة أو فعل محدد حسب مصدر الحالة، ولا يجعلان كل الصفوف معطلة دون سبب. الاستبدال بالمفتاح لا يكرر التفعيل؛ لا record-store أو sorting تجاري أو pagination هنا.

**معايير القبول:** سياقان مستقلان ببيانات معلنة، صف ساكن وآخر برابط وأفعال وإفصاح، نص عربي/لاتيني طويل وقيم طويلة، صفر/فراغ/خطأ/تعطيل فعل، لوحة المفاتيح وعدم تضاعف الحدث،360 RTL و320 فقط لإثبات الالتفاف عند الحاجة. روابط المصدر وأسماء الأفعال ليست مسارات Micro.

## C03 — سطح نموذج وطبقة قابلة للتحكم — وصفة منفذة للمراجعة

**الأساس:** Fields/Selection/Buttons/Messages داخل سطح CSS مشترك؛ Navigation خيار مستقل حين يختاره المضيف. المثال الثاني يستخدم `<dialog>` الأصلي وcancel القابل للمنع عند المتصفح، بمستهلك محلي يملك سياسة الإغلاق؛ لا يرتبط بمحرك Navigation ولا ينفذ D01. ليست Access Gateway عامة لكل نموذج، وليست محرك نموذج أعمال أو حالة draft.

- **المصدر:** form دلالي؛ label/hint/error مرتبط بكل حقل، ونوع زر submit/button صريح. القيم الخام والصحة وdirty والنسخة المعتمدة ونتيجة الحفظ مملوكة للمستهلك التجريبي الخارجي. لا مالية أو مسودة أو تخزين أو مصادقة داخل التركيب.
- **التحديث:** prefill عبر source + sync الصامت حيث ينطبق. لا يصنف كل حدث Picker/Carousel أو كل rerender تعديلًا من المستخدم. النص غير الصالح لا يختفي لإخفاء dirty؛ تطبيع quantity المقصود يبقى بعقده الخاص، ولا نفرض سياسة raw واحدة على كل نوع.
- **الإرسال:** انتظار مرتبط بوعد/حالة يقدمها المستهلك، منع الإرسال المكرر أثناءه، وخطأ بشري دون مسح الحقول أو إخفاء الخطأ الحرج في Toast مؤقت. لا مؤقت نجاح ولا اعتبار undefined/false أو اكتمال callback نجاحًا. العقد التجاري للنتيجة يحدده المستهلك؛ لا مخطط authenticated لكل نموذج.
- **الطبقة:** مالك واحد للتركيز/inert/scroll. إغلاق نية المستخدم يختلف عن أمر إغلاق بعد حفظ مؤكد أو إزالة الجذر. حارس dirty، إن وجد، عند المستهلك، وHistory/Back عند المضيف. لا نموذجان يديران التركيز على الطبقة نفسها.
- **التنظيف:** يفصل مستمعي التركيب ويوقف تحديث UI المتأخر وينظف كل طفل يملكه. لا يمنع disconnect بسبب اعتراض الإغلاق. إلغاء الشبكة مهمة مالكها، لا أثر ضمني لتنظيف DOM.

**معايير القبول:** نموذج inline وآخر في طبقة مستقلان، صالح/فارغ/غير صالح وreadonly/disabled/pending/خطأ، prefill لا يولد تعديلًا زائفًا، كتابة خام غير صالحة تبقى مرئية، تغيير callback لا يكرر الربط، Promise بعد إزالة الجذر لا تكتب فيه، إغلاق عادي/مرفوض/مقبول وتنظيف أثناء pending. قياس360 RTL، مع خطأ طويل وتركيز صالح ودون محتوى محجوب؛ لا خدمات أو History حقيقية.

## D01 / UX-06 — اقتراح طلب إغلاق قابل للاعتراض

**الوضع الحالي المؤكد:** Navigation.closeLayer أمر مباشر؛ Escape وزر الإغلاق والخلفية المسموح بها تستعمله. opened/closed إشعارات بعد تغير الحالة وليسا أحداثًا قابلة للإلغاء قبل الإغلاق. هذا احتياج استهلاك مشروط، لا إثبات عيب في الحوار وفق عقده الحالي.

**التوصية للمراجعة قبل الكود:** توسعة إضافية داخل Navigation، وليست dirty store:

| السطح المقترح، غير الموجود حاليًا | المعنى |
|---|---|
| `requestClose(layer,{reason?,trigger?})` | مسار نية إغلاق فقط؛ reason افتراضي programmatic-request. |
| `micro-navigation:close-request` | CustomEvent على الطبقة، bubbles=true وcancelable=true؛ detail `{reason,trigger}`، trigger عنصر أو null، لا dirty أو بيانات form. |
| نتيجة requestClose | false عند منع الطلب أو عدم وجود طبقة مفتوحة صالحة، true عند قبول بدء الإغلاق؛ ليست Promise ولا تأكيد closed. هذا توقيع مقترح للمراجعة. |

- الأسباب المقترحة المحددة: escape، close-button، backdrop، programmatic-request. لا reason=Back ولا قراءة URL. الخلفية keep لا ترسل طلبًا أصلًا؛ Escape لأعلى طبقة فقط.
- يرسل الطلب **قبل** تعديل المكدس أو focus أو hidden أو inert أو scroll. `preventDefault()` متزامن يمنعه؛ لا حدث closed ولا فقدان تركيز/قفل بسبب الرفض. لا مستمع يعني السلوك الحالي نفسه.
- إن احتاج المضيف قرارًا غير متزامن، يمنع الطلب أولًا ويدير تأكيده خارجيًا، ثم يستدعي closeLayer مباشرة عند القبول. لا تُنتظر Promise من dispatchEvent، ولا يتكرر التأكيد بعد القبول.
- `closeLayer` الحالي يبقى أمرًا صريحًا متوافقًا، وdisconnect يظل تنظيفًا إجباريًا لا يمكن منعه. الطبقة المغلقة/التي بدأت إغلاقها لا تولد طلبًا مكررًا. القبول لا يعد بانتهاء transition فورًا.
- **مدى التحويل المقترح:** Escape العام وزر data-layer-close والخلفية close فقط. استدعاءات Picker/AccountSettings والفلاتر والحفظ المباشرة تبقى أوامر حالية إلى أن يوثق كل مستهلك سبب التحويل على حدة؛ لا ادعاء أن المقترح يحرس كل خروج قائم. استعمال C03 المحروس لاحقًا يمر عبر requestClose صراحة لأفعال dismissal التي يملكها.
- تطبيق/إلغاء الفلاتر لهما عقد draft/applied قائم؛ لا يُعاد تعريفهما تلقائيًا كخروج dirty من نموذج عام. لا تغيير ترتيب أحداثهما بهذه الوثيقة.

**اختبارات التنفيذ المطلوبة:** منع كل سبب وإجازته، غياب المستمع، backdrop keep، عدم التغيير عند المنع، مرة واحدة لأعلى طبقة، repeated/closed/closing/no-op، قبول async ثم command، طبقات متداخلة، disconnect أثناء الرفض/الانتظار، حفظ API والفلاتر الحالية. قرار المرحلة2: **موصى به للمراجعة، غير منفذ**؛ إن اختير محرك مضيف أصلًا فلا نركب محركي modal معًا.

## D02 / UX-07 — القائمة ليست Picker

القرار الحالي: **تأجيل تنفيذ Menu مستقلة**. لم تثبت هذه المرحلة حاجة عامة تتجاوز وصفة أفعال واضحة، ولا يجوز إلباس أوامر تعديل/حذف role=option. Picker يبقى listbox لاختيار قيمة.

أفعال قليلة واضحة يمكن عرضها أزرارًا/روابط دلالية داخل سطح Navigation بدورة Tab العادية؛ لا نسمي هذا ARIA menu ولا نعد بأسهم menu. يجوز للمضيف مستقبلًا امتلاك controller مختلف دون نسخة من المصدر المشترك.

إذا أثبت سياقان مستقلان الحاجة إلى command-menu، نراجع أولًا عقد trigger وaria-expanded/controls، menuitem/disabled/تسمية الفعل، Arrow/Home/End/Escape وإعادة التركيز، موقع الطبقة ومالكها، وانتشار الأحداث والتنظيف. عندها فقط يحدد مصدره داخل Navigation أو تركيب مستقل؛ لا عائلة15 تلقائيًا. لا اعتماد على CSS أو سلوك Micro القديم لإثبات الحاجة.

## D03 / UX-08 — ملخص التقويم خارجي أولًا

القرار الحالي: **لا توسيع بيانات الطلب أو DOM التقويم الآن**. read-only summary خارجي C01 من المصدر الذي يملكه المستهلك، ومزامنة الحالة الحالية عبر getState وstate-change/day-select، والتحديث البرمجي من مالك setter نفسه لأنه صامت. لا انتظار حدث لن يصدر من setter ولا كتابة داخل الجذر المملوك للتقويم.

لا نفترض أن التنقل بين الأشهر يغيّر selectedDate؛ displayedMonth منفصل عنه بالفعل. يحدد المستهلك بوضوح هل الملخص يصف اليوم المحدد أم الشهر المعروض. لا حساب سعة أو تكرار أو دخل في Calendar.

إن أثبت مثالان أن معلومة على مستوى الطلب يجب أن توجد داخله ولا يكفي الملخص الخارجي، تُعرض حاجة metadata/slot عامة بعقد تطبيع نص آمن وتحديث وتنظيف وإتاحة قبل الكود؛ لا حقول خاصة بمضيف أو حقن HTML غير محدود. لا حذف صامت للحد الحالي: normalizeOrders يحتفظ بالحقول الموثقة فقط.

## ترتيب التنفيذ بعد المراجعة

1. المرحلة3 اكتملت كتدقيق مستقل للمصدر والحالات وإصلاحات بدليل؛ سجلها محفوظ دون تغيير تاريخ نتائجه.
2. المرحلة4 نفذت C01 ثم C02 ثم C03، مع سياقين ومصدر مشترك واختبارات لكل تركيب، بحالة Draft للمراجعة. D01 غير منفذ ويحتاج اعتمادًا صريحًا؛ مثال C03 المحروس يستخدم native dialog وcancel عند المتصفح. D02/D03 دون توسعة.
3. المرحلة5: حاضنات عامة لاختلاف الحاويات وCSS/RTL والطبقات والتحديث، من دون تشغيل Micro أو تقليد عيوبه كعقد. بعدها فقط نعود للرسوم في المرحلة6؛ النسب حيث تلزم فقط.

**حد التسليم:** اكتمال هذه العقود لا يعني أن المكتبة اجتازت التدقيق البصري اللاحق أو اختبارات الهاتف الحقيقي، ولا أنها مركبة أو مقبولة داخل Micro.
