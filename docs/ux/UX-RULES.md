# قواعد UX مستقلة — V0.1

الحالة: **DRAFT FOR REVIEW**. هذه قواعد سلوك مقترحة للتطبيق، لا قرار اعتماد لكل رحلة. معرفات المراجع في [SOURCES](SOURCES.md). «المطلوب» هنا شرط تسليم المشروع؛ لا يصبح معيارًا دوليًا إلا في حدود المرجع المذكور. أمثلة القيم والأسماء تركيبية.

## الأفعال والنتائج

### UX-01 — معنى الإجراء
- المطلوب: اسم يصف النتيجة، مع فصل الفتح والتنقل عن تغيير البيانات. راعِ الفرق بين «حفظ» و«تطبيق» و«إرسال»؛ لا تختَر اسمًا قبل معرفة أثره.
- صحيح/مرفوض: «عرض التفاصيل» لفتح قراءة / «حفظ» يفتح صفحة بلا حفظ.
- القبول: ينص عقد الإجراء على أثر الضغط ونقطة النجاح؛ يطابق الاسم النتيجة في المثال.
- الأساس: P، G1؛ يحتاج المستهلك تحديد الأثر.

### UX-02 — ترتيب الأفعال
- المطلوب: فعل حاسم بارز لكل مجموعة قرار؛ دعم وإلغاء ببروز مناسب. لا تعمم ذلك على الصفحة كلها أو تخفِ البدائل الضرورية.
- صحيح/مرفوض: حفظ رئيسي وإلغاء ثانوي / عدة أفعال متساوية البروز دون هدف واضح.
- القبول: يستطيع المراجع تسمية القرار الأساسي في المجموعة وسبب بروز كل فعل.
- الأساس: P؛ لا رقم دولي مفروض للأزرار.

### UX-03 — التنفيذ الجاري ومنع التكرار
- المطلوب: حالة pending مفهومة وحراسة للتفعيل المكرر. نجاح الواجهة يتبع نتيجة المستهلك، لا انتهاء مؤقت أو زوال المؤشر. الحراسة في UI ليست ضمان منع معاملات مكررة في الخادم.
- صحيح/مرفوض: نتيجة مؤكدة ثم «تم الحفظ» / نجاح تلقائي بعد ثانيتين رغم رفض الطلب.
- القبول: النقر وEnter/Space المتكرر أثناء pending لا يطلقان طلبًا إضافيًا؛ الفشل يعيد إمكانية التصحيح.
- الأساس: P، W4؛ سياسة تكرار الشبكة مسؤولية التطبيق.

### UX-04 — التأكيد بحسب الأثر
- المطلوب: للإجراء ذي العواقب، حدد الرجوع الممكن وخطورة الفقد قبل اختيار المراجعة/التأكيد. لا تأكيد متكرر للإجراء العادي القابل للتراجع، ولا تراجع مزيف لإجراء غير قابل للعكس.
- صحيح/مرفوض: ذكر أثر الحذف غير القابل للتراجع وإلغاء واضح / «هل أنت متأكد؟» بلا سياق لكل نقرة.
- القبول: بطاقة المهمة تصف الأثر وإمكان التراجع والحماية المختارة. شروط W3 تطبق فقط على الحالات المشمولة.
- الأساس: W3، I1/I2، P؛ نوع الإجراء مجهول حتى يعرّفه المستهلك.

### UX-05 — تعديل محلي مقابل حفظ مثبت
- المطلوب: افصل القيمة المعروضة عن القيمة المؤكدة. عند السماح بالتراجع بينهما وثّق استعادة الأصل. حفظ تلقائي أو صريح قرار يحدد لكل مهمة ولا يُفترض.
- صحيح/مرفوض: «تغييرات غير محفوظة» حتى النجاح / اعتبار تغيير DOM حفظًا.
- القبول: رفض الحفظ لا ينتج رسالة نجاح ولا يمحو التعديل؛ dirty يزول فقط عند الاستعادة أو التأكيد.
- الأساس: P؛ يحتاج تعريف dirty والمساواة وتوقيت الحفظ من المستهلك.

### UX-06 — المغادرة والتغييرات غير المحفوظة
- المطلوب: فرّق بين إغلاق قراءة ومغادرة تعديل. عندما توجد تغييرات معرضة للفقد، أتح مسار البقاء أو الحفظ أو التخلي المناسب. لا تحذير لنموذج لم يتغير؛ العودة لا تنفذ التخلي تلقائيًا.
- صحيح/مرفوض: البقاء يحفظ الإدخال والتركيز / إغلاق الطبقة يمحو نموذجًا متغيرًا دون سياسة.
- القبول: جرّب رجوعًا وإغلاقًا وإلغاءً على نموذج clean وdirty؛ pending له سياسة صريحة، لا يُقال «أُلغي الحفظ» لمجرد إغلاق العرض.
- الأساس: P، I2، G2 على المنصة؛ حراسة رجوع النظام تحتاج تركيبًا لاحقًا.

## الإدخال والاختيار

### UX-07 — التسمية والمساعدة
- المطلوب: اسم دائم للحقل، وحدة وصيغة عند الحاجة، ومساعدة محلية موجزة دون إخفاء تعليمات لازمة. لا تستخدم placeholder بدل الاسم.
- صحيح/مرفوض: «الكمية» + الوحدة / حقل فارغ لا يعرف المستخدم غرضه بعد الكتابة.
- القبول: الاسم الإتاحي يبقى بعد الامتلاء، والمساعدة اللازمة مرتبطة بالحقل.
- الأساس: W2، P؛ حد سطرين للمساعدة دليل تحرير لا سقف يخفي معلومة ضرورية.

### UX-08 — غياب القيمة وحالاتها
- المطلوب: فارغ، صفر، قيمة ممتلئة، خطأ ونجاح تحقق حالات مختلفة. النجاح لا يُستنتج من الامتلاء، ولا يُحوّل الغياب إلى 0.
- صحيح/مرفوض: قيمة 0 صريحة / عرض علامة نجاح فور كتابة حرف.
- القبول: أمثلة فارغ/0/ممتلئ غير متحقق/خطأ/نجاح ذي سبب، مع بقاء المحتوى عند الخطأ.
- الأساس: P؛ الحسابات وصحة القيمة التجارية خارج القاعدة.

### UX-09 — توقيت التحقق
- المطلوب: في البداية لا تُدان الحقول الفارغة. عند محاولة الإرسال افحص المطلوب؛ بعد معرفة خطأ محدد أعد تقييمه عند التصحيح بتوقيت مناسب. التحقق عند الخروج أو أثناء الكتابة يذكر سببه ولا يعمم.
- صحيح/مرفوض: خطأ مطلوب بعد الإرسال / رسالة خطأ حمراء على أول فتح للنموذج.
- القبول: اختبار فتح→كتابة جزئية→إرسال→تصحيح؛ لا رسائل قديمة بعد زوال سببها.
- الأساس: توقيت المشروع P؛ وصف الأخطاء W1، ولا يفرض W1 توقيت blur.

### UX-10 — التصحيح والمحافظة على الإدخال
- المطلوب: سمِّ موضع الخطأ وسببه وكيفية علاجه حيث معروفة، مع وصف مرتبط وحفظ بقية القيم. أخطاء الشبكة ليست خطأ صيغة في الحقل.
- صحيح/مرفوض: «أدخل الاسم للمتابعة» / «حدث خطأ» مع تفريغ جميع الحقول.
- القبول: الإرسال غير الصالح يتيح الوصول للأخطاء؛ التصحيح لا يفقد القيم السليمة أو سياق النموذج.
- الأساس: W1، P؛ النص النهائي يعتمد على تحقق المستهلك.

### UX-11 — المعطل والقراءة فقط
- المطلوب: readonly للقراءة/النسخ، disabled لعدم توفر التفاعل. إذا تعطل إجراء مطلوب، اجعل سببًا واضحًا ومسارًا لتجاوزه إن أمكن؛ لا تمنع الوصول إلى شرح السبب بتعطيله.
- صحيح/مرفوض: مبلغ مقروء قابل للنسخ / إخراج كل قيم القراءة من الوصول.
- القبول: فحص النسخ، التبويب، تكرار pending، والحالة المعطلة أصلًا دون إعادة تمكين خاطئة.
- الأساس: P؛ عقود HTML وUI الحالية تحفظ الفرق.

### UX-12 — اختيار نوع التحكم
- المطلوب: radio لواحد، checkbox لمتعدد مستقل، switch لإعداد on/off، toggle لوضع مؤقت، tabs لتبديل محتوى. لا switch للتنقل أو إرسال نموذج.
- صحيح/مرفوض: مفتاح تفعيل إعداد مع اسم واضح / مفتاح يفتح صفحة جديدة.
- القبول: دور التحكم وحالته الإتاحية يطابقان وظيفته؛ يُعرّف تطبيق الاختيار فورًا أو عبر حفظ مستقل.
- الأساس: P، W5؛ لا فرض نوع حفظ واحد على كل إعداد.

### UX-13 — تحديث الإعداد غير المتزامن
- المطلوب: للمفتاح الذي يطلب حفظًا، وثّق هل يظهر التغيير مؤقتًا أو بعد التأكيد. عند رفض مثبت، تعود القيمة المؤكدة مع تفسير؛ عند نتيجة غير معروفة لا تدّعِ نجاحًا أو فشلًا مؤكدًا.
- صحيح/مرفوض: pending→رفض→استعادة معلنة / تبديل بصري يبقى «محفوظًا» بعد رفض المستهلك.
- القبول: تكرار التفعيل لا يتقاطع؛ pending لا يعيد تمكين disabled الأصلي؛ انتهاؤه لا يقرر القيمة وحده.
- الأساس: P؛ API الإعداد والشبكة للمستهلك.

### UX-14 — المنتقي والبيانات المتجددة
- المطلوب: loading/error/empty ليست نتائج قابلة للاختيار. البحث لا يزيل حالة القراءة؛ عند سقوط الاختيار من بيانات جديدة، حدّث الملخص والقيمة معًا، ولا تختر بديلًا تلقائيًا.
- صحيح/مرفوض: خطأ مع إعادة محاولة / نتائج قديمة قابلة للاختيار أثناء القراءة الفاشلة.
- القبول: ready→loading→error→retry→ready، واختفاء المحدد، والملاحة باللوحة؛ نختبر عقد المنتقي الحالي لا نفرض دور combobox على حوار.
- الأساس: P، A2 إرشاد لاختيار النمط حين ينطبق.

### UX-15 — البحث والفلاتر والسياق
- المطلوب: افصل تعديل الفلاتر الجاري عن المطبّق. تطبيق يقر، إلغاء يحافظ على المطبّق، ومسح الجاري لا يعني إزالة الفلاتر قبل تطبيقها. لا نتائج ليست لا بيانات ولا فشل قراءة.
- صحيح/مرفوض: ملخص للفلاتر المطبقة مع إمكان تعديلها / اختفاء القائمة بمؤشر «0» عند انقطاع الشبكة.
- القبول: apply→edit→cancel يحافظ على النتيجة السابقة؛ اختبار البحث مع الفلاتر والمسح.
- الأساس: P، W4 عند إعلان تحديث النتائج؛ حفظ الموضع عبر الصفحات للمستهلك.

## التنقل والتغذية الراجعة

### UX-16 — الرجوع والتنقل المتوقع
- المطلوب: حدّد هل الفعل يرجع أو يغلق طبقة أو ينتقل لوجهة؛ لا تبديل سياق غير معلن لمجرد إدخال قيمة. حافظ على سياق الوصول حيث يناسب المهمة.
- صحيح/مرفوض: إغلاق المنتقي يرجع للنموذج / تغيير حقل ينقل لصفحة بلا إشعار مسبق.
- القبول: مسار الرجوع مكتوب؛ موضع القائمة/بحثها عند العودة يختبر بعد معرفة نموذج التنقل.
- الأساس: W5، G2 للغلاف؛ لا نرسم خريطة شاشات هنا.

### UX-17 — الحوار والتركيز
- المطلوب: افتح modal بهدف واضح؛ اعزل الخارج واحصر التركيز، مع إغلاق ظاهر ولوحة مفاتيح. استعد التركيز للمشغّل أو هدف منطقي إذا أزيل؛ لا تجعل Escape طريقًا صامتًا للتخلي عن dirty.
- صحيح/مرفوض: إغلاق قراءة يعيد التركيز / تركيز في BODY أو عنصر inert بعد الإغلاق.
- القبول: Tab/Shift+Tab/Escape، طبقة متداخلة، إعادة فتح أثناء الخفوت، مشغّل أزيل، وسياسة خلفية مناسبة.
- الأساس: A1، P؛ حراسة فقد التعديل من المستهلك وتتطلب ربطًا صريحًا، لا نفترض أن B07 يطبقها.

### UX-18 — قناة الرسالة
- المطلوب: خطأ الإدخال قرب الحقل، وفشل مهمة برسالة باقية ومسار عمل، وToast لنتيجة غير حرجة مع بديل ثابت وفق عقد المكتبة. لا تجعل رسالة مطلوبة للاستكمال تختفي وحدها.
- صحيح/مرفوض: «تعذر الحفظ، حاول مجددًا» باقية / إخفاء سبب فشل الإرسال بعد مهلة قصيرة.
- القبول: المعلومة المهمة متاحة بعد انتهاء المؤقت؛ لا تُنقل تفاصيل debug إلى نص المنتج.
- الأساس: P، W1/W4 للإتاحة، I1 للمقاطعة؛ لا مدة Toast معيارية هنا.

### UX-19 — إعلان الحالة دون مقاطعة
- المطلوب: اعلان مفيد عند تغير الحالة، دون تكرار أو نقل تركيز لكل تحديث. لا تجعل كل رسالة أو كل حرف alert؛ اضطرار المستخدم لمعالجة خطأ له سياسة تركيز معلنة.
- صحيح/مرفوض: نتيجة بحث معلنة مرة / إعلان الاسم والعداد نفسه عدة مرات.
- القبول: مصدر إعلان واحد، حفظ التركيز أثناء التحديث غير الحواري؛ قارئ شاشة فعلي لاحقًا.
- الأساس: W4؛ دور الرسالة وشدتها لا يُنسخان آليًا إلى كل سياق من مثال UI.

### UX-20 — القراءة وإعادة المحاولة
- المطلوب: ميّز لا بيانات/لا نتائج/خطأ/pending/محتوى مثبت قديم. ظهور القديم أثناء التحديث قرار معلن؛ لا تقدمه كقراءة حديثة ولا تسمح بعملية على بيانات غير صالحة.
- صحيح/مرفوض: القراءة القديمة موسومة مع إعادة محاولة / إعادة الطلب تُظهر صفحة فارغة بعنوان «لا بيانات».
- القبول: فشل→retry→success، ورد متأخر لا يكتب فوق نتيجة أحدث؛ لا يختلق المثال شبكة فعلية.
- الأساس: P، W4؛ stale-policy وإلغاء الطلبات للمستهلك.

### UX-21 — السحب والحركة
- المطلوب: السحب اختياري مع أزرار/وسيلة دون سحب؛ الحركة توضح التغير ولا تكون دليله الوحيد، وتقليل الحركة يحافظ على الوظيفة. لا autoplay افتراضي.
- صحيح/مرفوض: A05 بأسهم ومؤشر مفهوم / سحب لا بديل له أو تبديل تلقائي يمنع القراءة.
- القبول: touch/keyboard/pointer حيث متاح، reduced-motion، 0/1/عدة بطاقات وتركيز بطاقة تصبح غير نشطة.
- الأساس: W6، P؛ نمطا A05 معتمدان كخيارات، لا يفرضان على الرئيسية.

## المعنى والمحتوى والمنصات

### UX-22 — القراءة والرسوم الصادقة
- المطلوب: الاسم والوحدة والفترة وتعريف المقام من المستهلك؛ الغياب ليس 0، واتجاه التغير ليس حكمًا بأنه جيد. اختر الرسم المناسب، ووفّر القيم والمعاني خارج اللون وحده.
- صحيح/مرفوض: مقارنة لفترة معلنة / نسبة من مقام مفترض أو زيادة ملونة نجاحًا مهما كان معناها.
- القبول: صفر/غياب/سالب/مقام غير صالح/فجوة زمنية؛ لا تقريب أو توسعة صامتة تغير معنى البيانات.
- الأساس: P، W10؛ صحة الحساب ومصدر البيانات لا يثبتان بصورة الرسم.

### UX-23 — تفاصيل تدريجية ومحتوى موجز
- المطلوب: اعرض المعلومات اللازمة لاتخاذ الإجراء في موضعها، والتفاصيل الإضافية عند الطلب؛ لا تُخفِ أثرًا حاسمًا أو شرطًا لازمًا للتوفير البصري.
- صحيح/مرفوض: عنوان + صفوف + شرح محلي / مقدمات وتحذيرات متكررة قبل كل تحكم.
- القبول: لكل نص سبب وموضع؛ يستطيع المستخدم معرفة ما يفعل وما سيحدث دون فتح شرح عام طويل.
- الأساس: P، W2 للتعليمات اللازمة؛ لا نحسم نصوص المنتج هنا.

### UX-24 — الصف والهدف القابل للتفاعل
- المطلوب: ميّز صف القراءة عن صف الفتح وعن الإجراء داخله. لا مناطق ضغط متداخلة ولا إجراء خفي على الصف كله.
- صحيح/مرفوض: هدف تفاصيل وإجراء منفصلان / زر حذف داخل رابط يغطي الصف.
- القبول: لكل هدف اسم وأثر وتركيز؛ نقر الإجراء لا يفتح التفاصيل معه.
- الأساس: P، G1؛ لا نستنتج clickability من وجود بطاقة.

### UX-25 — هاتف وتكبير ولمس
- المطلوب: لا قص للمحتوى اللازم، ولا حجب كامل للتركيز بشريط ثابت. هدف لمس المشروع من tokens، وتحويل native يتبع وحدات المنصة؛ يختبر على الجهاز، لا يستنتج من CSS.
- صحيح/مرفوض: النص يكبر والتحكم يتمدد / تصغير الخط أو قص المبلغ للحفاظ على ارتفاع ثابت.
- القبول: 320/360/390/430، تكبير 200% معلن الآلية، لوحة الهاتف والحواف الآمنة؛ فرق CSS px وdp محفوظ.
- الأساس: W7/W9/W11، G1؛ 48px سياسة المكتبة ليست ادعاء حد WCAG AA.

### UX-26 — العربية والاتجاه
- المطلوب: RTL في البناء، عزل القيم والأسماء المختلطة عند الحاجة، أرقام 0–9 حسب الهوية، واتجاه رموز التنقل بحسب معناها. لا قلب للعلامة التجارية وكل الأيقونات.
- صحيح/مرفوض: مبلغ وسالب ووحدة مقروءة / إشارة ناقص منفصلة عن الرقم بسبب الاتجاه.
- القبول: اسم مختلط طويل، مبلغ سالب، نص ملتف، أسهم وتنقل وترتيب قراءة منطقي.
- الأساس: P؛ لا تحويل عملة أو تقويم أو تنسيق أعمال صامت.

### UX-27 — الوصول والقدرة على التنفيذ
- المطلوب: لا تعرض نجاح دخول أو حفظ لأن callback انتهى فقط دون عقد نتيجة. إظهار خيار يحتاج قدرة فعلية؛ لا توهم استعادة وصول أو تراجع أو إجراء غير متاح. حافظ على وسائل المصادقة المساعدة حيث تنطبق.
- صحيح/مرفوض: handler مُعلن ومسار فشل / مزود دخول ظاهر بلا وظيفة أو منع لصق كلمة المرور افتراضيًا.
- القبول: غياب handler معلن، رفضه لا يعطي نجاحًا، لا أسرار في بيانات الاختبار؛ صلاحيات الخدمة ليست حماية يحققها إخفاء الزر.
- الأساس: P، W8 للمصادقة؛ الأمن والمصادقة والحفظ خارج المكتبة.

### UX-28 — المجهول لا يُملأ بافتراض
- المطلوب: عند غياب نوع الحفظ/الأثر/الصلاحية/الوحدة/المقام/الوجهة، سجل القرار الناقص وأوقف الجزء المعتمد عليه. يستمر العمل المستقل؛ لا يتحول مثال تركيبي إلى قاعدة أعمال.
- صحيح/مرفوض: سؤال محدد عن نقطة الالتزام / اعتبار كل ضغط محفوظًا ماليًا أو نجاحًا اعتمادًا على شكل الزر.
- القبول: لكل قرار عمل مصدر معلومة واضح؛ كل مجهول يُوسم NEEDS PRODUCT INPUT بدل اختراع endpoint أو نص أو رحلة.
- الأساس: P؛ هذا عقد عمل للـAgent لا معيار دولي.
