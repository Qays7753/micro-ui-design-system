# مواصفة إصلاح UI لنظام Micro الجديد

## UI Root-Cause Repair Specification — Baseline `main@496b900`

- **المستودع:** `Qays7753/micro-ui-design-system`
- **خط الأساس:** `main@496b900ab41085627ca0a8f9479674a9dc3ad677`
- **نطاق التنفيذ:** مكونات UI الحالية الموجودة في المستودع ومعايناتها ومواصفاتها فقط.
- **مرجع الشكل:** [تصور UI البصري](./UI-SYSTEM-VISUAL-CONCEPT-AR-EN.md)
- **مرجع الأدلة:** [التقرير المرجعي الكامل](./MASTER-UI-SYSTEM-AUDIT-496b900.md)
- **المنفذ:** Zed AI
- **حالة الوثيقة:** عقد تنفيذ؛ لا تعدّل المصدر بنفسها.

> هذه الوثيقة تحدد طريقة إصلاح المكونات الحالية من جذورها، لا طريقة تصميم منتج أو صفحات جديدة.

## 1. قفل النطاق

### 1.1 ما يجب إصلاحه الآن

الإصلاح الحالي يقتصر على ما يلي:

- `shared/tokens.css` والتوكنز المرتبطة بالمكونات.
- CSS وJavaScript وHTML للمكونات الحالية.
- مواصفات المكونات الحالية.
- معاينات المكونات الحالية والـfixtures اللازمة لإثبات الإصلاح.
- الهندسة البصرية: القياسات، المسافات، الحواف، المحاذاة، الطباعة، السطوح، والحركة الموجودة.
- حالات UI: default، hover عند انطباقه، pressed، focus، selected، disabled، loading، busy، pending، error، success، empty، long text.
- دلالات المكونات الحالية وسلوكها المرتبط مباشرة بالمكوّن.
- RTL/LTR والخصائص المنطقية للمكونات الحالية.
- مكونات البيانات والرسوم الحالية من ناحية الهندسة، العقد، الصدق البصري، والوصول إلى بياناتها.
- التراكيب الحالية الموجودة أصلًا، مثل tabs وnavbar وactionbar وlayer وsheet وdialog، من ناحية ملكية المساحة والحالات والتداخل.

### 1.2 ما لا يُنفذ ضمن هذه الجولة

لا يضيف Zed AI أو يصمم أو يفترض:

- صفحات أو رحلات أو بنية منتج.
- منطق أعمال أو صلاحيات أو قواعد منتج.
- عائلات مكونات جديدة غير موجودة.
- تغيير الهوية البصرية أو قيمها.
- طبقة منتج أو تطبيق خارج المكونات الحالية.
- وظيفة تكبير أو تغيير مقياس UI.
- أي قرار لا يوجد له عقد في هذه الوثيقة أو مرجع رسمي أو قرار مالك مكتوب.

أي Finding موجود في التقرير الكامل لكنه غير مذكور ضمن موجات التنفيذ أدناه يُعامل كدليل تدقيقي مؤجل، وليس كأمر تنفيذ.

### 1.3 قاعدة التكبير

أي قياسات سابقة استخدمت تكبير المتصفح أو محاكاة حجم النص هي **أدلة تشخيصية على وجود overflow أو ارتفاعات جامدة** فقط. لا تعني أن النظام يجب أن ينفذ وظيفة تكبير، ولا تعني أن Zed AI يضيف scale control أو يغيّر مقياس UI.

معيار الإصلاح هو ثبات المقياس البصري للمكونات الحالية، وعدم قص النص أو الرقم، وعدم اختلاف المكوّن نفسه بين المعاينات.

### 1.4 قاعدة ألوان الهوية

- لا يغير Zed AI ألوان الهوية الحالية.
- يستخدم القيم والتوكنز الموجودة فعليًا في `shared/tokens.css` على `main` الحالي.
- لا يضيف قيمة أو درجة أو gradient أو role لونيًا جديدًا ضمن الإصلاح.
- إذا رأى أن هناك اقتراحًا لونيًا أفضل، يحافظ على القيمة الحالية ويضع الاقتراح فقط في تقرير ما بعد التنفيذ تحت:
  ```text
  COLOR PROPOSAL — NOT IMPLEMENTED
  ```
- يجب أن يحتوي الاقتراح على اسم التوكن والقيمة الحالية الدقيقة والقيمة المقترحة الدقيقة إن وجدت والسبب والدليل والمكونات المتأثرة.
- لا يُنفذ أي تغيير لوني دون قرار مالك مستقل بعد انتهاء إصلاحات UI.

## 2. قاعدة المصدر والفروع

### 2.1 `main` هو خط الأساس وليس فرع التنفيذ

قبل إنشاء فرع الإصلاح:

```bash
git fetch origin main
git checkout main
git pull --ff-only origin main
git status --short --branch
git rev-parse HEAD
git rev-parse origin/main
```

إذا لم يساوِ `HEAD` قيمة `496b900ab41085627ca0a8f9479674a9dc3ad677` أو إذا تغيّر `origin/main`، يتوقف Zed AI ويسجل رأسًا جديدًا قبل قراءة الأدلة التنفيذية.

### 2.2 فرع إصلاح واحد فقط

- ينشئ Zed AI فرعًا واحدًا من آخر `main`، مثل:
  ```text
  zai/ui-root-cause-repair
  ```
- تنفذ جميع إصلاحات هذه الجولة على هذا الفرع فقط.
- لا يُعدّل `main` مباشرة.
- لا تُنشأ فروع فرعية لكل موجة.
- لا تُوزع الإصلاحات على فروع متنافسة.
- `main` يبقى baseline للمقارنة والدمج لاحقًا.

### 2.3 قاعدة العمل النظيف

إذا وُجدت تعديلات غير متوقعة أو ملفات generated مختلفة أو مصدر لا يطابق الرأس المرجعي، يتوقف Zed AI قبل التعديل ويبلغ عن:

```text
BASELINE MISMATCH
```

## 3. هرمية الأدلة وقاعدة عدم الاختراع

كل قرار إصلاح يجب أن يصنف إلى واحد من الآتي:

- `NORMATIVE`: مفروض بمرجع رسمي منطبق.
- `CURRENT TOKEN`: قيمة موجودة في المصدر الحالي يجب الحفاظ عليها.
- `CURRENT COMPONENT CONTRACT`: سلوك موثق للمكوّن الحالي.
- `OWNER DECISION`: اختيار لا يُحسم بصمت.
- `DIAGNOSTIC`: قياس أو probe يثبت مشكلة، لكنه لا يحدد الحل وحده.

### 3.1 المراجع الأساسية

- [WAI-ARIA Tabs](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/)
- [WAI-ARIA Modal Dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)
- [WAI-ARIA Names and Descriptions](https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/)
- [WAI-ARIA Live Regions](https://www.w3.org/WAI/ARIA/apg/practices/live-regions/)
- [MDN aria-disabled](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Attributes/aria-disabled)
- [MDN env()](https://developer.mozilla.org/en-US/docs/Web/CSS/env)
- [WCAG Target Size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)
- [WCAG Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)
- [Android Navigation Components](https://developer.android.com/develop/ui/compose/components/navigation-bar)
- [Material 3 States](https://m3.material.io/foundations/interaction/states)
- [Material Data Visualization Accessibility](https://m3.material.io/blog/data-visualization-accessibility)

مراجع Android هي مرجع جودة وتكوين، وليست إذنًا لنسخ الهوية أو اختراع قيم غير موجودة في المستودع.

### 3.2 القاعدة التنفيذية

إذا لم يملك Zed AI:

```text
Finding → root cause → owning file → contract → test → PASS evidence
```

فلا ينفذ البند. يسجله:

```text
NEEDS OWNER DECISION
```

أو:

```text
NOT PROVEN
```

ولا يستبدل نقص الدليل باجتهاد بصري.

## 4. قرارات UI التي يجب ألا يحسمها Zed AI بصمت

هذه قرارات تخص المكونات الحالية، لكنها ليست محسومة من الأدلة وحدها. يجب أن يظهر كل منها في Plan ببدائل واضحة، ثم يتوقف التنفيذ عنده إذا لم يوجد قرار مالك:

### D-UI-01 — سياسة تبويبات النص الطويل

اختيار واحد من:

1. التفاف مضبوط مع نمو ارتفاع الصف.
2. تمرير أفقي مقصود مع مؤشر وkeyboard behavior.
3. نمط تراص أو ترتيب بديل داخل المكوّن.
4. سقف واضح للتبويبات مع نمط موجود أصلًا في النظام.

الممنوع: القص، التصغير التلقائي، أو overflow مرئي صامت.

### D-UI-02 — ملكية دلالات الطبقات والرسائل

اختيار واحد من:

1. المكوّن يضيف defaults ويتحقق من الاسم والدور.
2. المستهلك يملك القيم، لكن validator يمنع التركيب الناقص.

الممنوع: ترك المستهلك يضيف role/name/modal/status بلا عقد أو فحص.

### D-UI-03 — سياسة فصل أهداف اللمس

لا تُفرض قيمة جديدة لمجرد أنها تبدو شائعة. يجب اعتماد قاعدة قياس تفصل بين حجم الهدف والفاصل بين bounding boxes، مع توثيق استثناءات stepper وcalendar grid إن بقيت.

### D-UI-04 — مسار البيانات البديل للرسم

يُحسم هل سيُعرض داخل مكوّن الرسم الحالي كـdisclosure أو dataset دلالي، أم أن الفجوة تحتاج قرارًا منفصلًا. لا تُنشأ عائلة جدول أو استكشاف بيانات جديدة ضمن هذه الجولة دون اعتماد.

### D-UI-05 — الشكل المرئي مقابل hit area

يُحسم ما إذا كان اختلاف الحجم المرئي عن hit area مقصودًا في Segmented والعناصر المشابهة. لا يُلغى أو يُفرض بصمت.

### D-UI-06 — أسماء توكنز runtime

يحافظ Zed AI على أسماء التوكنز الصحيحة الموجودة. لا يعيد تسمية namespaces على نطاق واسع ضمن إصلاح مكوّن، إلا إذا أثبت أن الاسم الحالي هو سبب مباشر وقدم mapping واختبارات وموافقة الخطة.

## Wave 1 — Geometry وNavigation Components

### W1.1 `m-tabs`

**الأدلة الحالية:**

- `components/navigation/navigation.css`
- `components/navigation/navigation.js`
- `components/navigation/specification.md`
- `previews/navigation/index.html`

**العقد المطلوب:**

- سياسة واحدة معلنة للتبويبات الطويلة.
- لا خروج صامت للمحتوى.
- لا قص ولا تصغير تلقائي.
- RTL/LTR لا يغيران معنى التبويب.
- `role=tablist`, `role=tab`, `role=tabpanel`, `aria-controls`, selection وfocus تبقى متزامنة.

**اختبار PASS:**

- عروض 320/360/390/430.
- نص عربي طويل ولاتيني طويل.
- لا overflow غير مقصود.
- السياسة المختارة قابلة للقياس وقابلة للاستخدام بالكيبورد.

إذا بقي D-UI-01 بلا قرار، يكتب Zed AI خطة الخيارات ولا يختار واحدًا صامتًا.

### W1.2 `tabpanel`

- اللوحة النشطة التي لا تحتوي هدفًا داخليًا قابلًا للتركيز تحصل على `tabindex=0` وفق نمط WAI-ARIA.
- لا يضاف tabindex عشوائي إلى لوحة لديها هدف داخلي مقصود.
- focus على tab ثم الانتقال التالي يصل إلى بداية المحتوى وفق العقد.
- التبديل لا يترك لوحة غير نشطة في ترتيب التركيز.

### W1.3 ملكية safe-area في التراكيب الحالية

- مالك واحد فقط للحافة الآمنة في كل تركيب.
- لا تضيف الأسطح الداخلية inset مكررًا.
- الاختبار يستخدم fixture موجبًا اصطناعيًا لأن قيمة Chromium الصفرية لا تكشف التكرار.
- لا يغيّر هذا البند هوية المكوّن أو يضيف طبقة منتج جديدة.

### W1.4 `navbar` و`actionbar`

- الارتفاع ينمو مع النص ولا يعتمد المستهلك على رقم ثابت.
- المحتوى التالي لا يتداخل مع الشريط.
- لا يكرر safe-area.
- CSS وJavaScript يتفقان على الارتفاع الفعلي.
- ResizeObserver، إن بقي، يكون جزءًا من عقد موثق لا تعليقًا غير منفذ.

### W1.5 touch geometry

- فحص bounding boxes الفعلية، لا `min-height` فقط.
- قياس الفصل بين الأهداف المتجاورة.
- تسجيل Segmented وstepper وcalendar كاستثناءات إن اعتمدت.
- لا يعتمد الاختبار على مساواة CSS px بـdp أو pt.
- لا تنفذ قيمة فصل جديدة قبل قرار D-UI-03.

### W1.6 picker والنص الطويل

- `min-inline-size:0` حيث يلزم.
- التفاف واضح للنص الطويل.
- لا ellipsis لاسم يحتاج قراءة كاملة.
- لا height ثابت يقص label أو option.

## Wave 2 — States وSemantics وTokens

### W2.1 `disabled` و`aria-disabled`

- المظهر والسلوك والدلالة متطابقة.
- hover/active لا يوحيان بالتفعيل.
- pointer وkeyboard وprogrammatic activation محروسة.
- قرار Tab order يسجل صراحة ولا يُترك للصدفة.

### W2.2 الطبقات الحالية

وفق D-UI-02:

- role/name/modal/description لها owner واضح.
- focus trap والاستعادة لا ينفصلان عن semantics.
- validator أو defaults يثبتان العقد.
- لا يُقبل layer ناقص فقط لأنه يبدو صحيحًا بصريًا.

### W2.3 الرسائل وlive regions

- status وalert وnote لا تُخلط.
- burst events لا تعتمد على timeout ثابت يسبب فقدان ترتيب.
- queue/coalescing أو القنوات المنفصلة قرار موثق.
- لا يعلن النظام نجاحًا أو خطأً بطريقة تختلف عن الحالة المرئية.

### W2.4 التوكنز والقيم الصلبة

- استخدم التوكنز الحالية عندما تمثل القرار نفسه.
- لا تنقل كل رقم إلى `:root` بلا سبب.
- لا تعيد تسمية كل namespaces دفعة واحدة.
- runtime geometry يملك namespace موثقًا ولا يخلط مع system token.
- أي rgba/hex داخل component يحتاج توكنًا قائمًا أو استثناءً مسجلًا.
- لا تغيّر أي قيمة لونية؛ راجع قفل الألوان في القسم 1.4.

### W2.5 `init(root)` وlifecycle

اعتمد contract واحدًا لكل عائلة بعد فحص source الحالي:

- root نفسه + descendants، أو
- container-only.

ثم اختبر:

- root node.
- container.
- dynamic mount.
- disconnect.
- re-init.
- عدم ازدواج listeners.

لا توحد API بتغيير واسع إذا لم يكن ذلك لازمًا لإغلاق Finding مثبت.

## Wave 3 — Data وCharts الحالية

### W3.1 اسم ووصف الرسم

- العنوان المرئي هو مصدر الاسم عندما يوجد.
- الوصف والsummary مرتبطان بالرسم الحالي.
- لا يبقى summary يصف بيانات قديمة بعد إعادة التصيير.
- type/unit/range/unknown/negative توصف عندما تكون جزءًا من بيانات المكوّن الحالية.

### W3.2 عقد المقياس

لـbars/line/bubbles الحالية:

- غياب max له سلوك موثق.
- max غير الصالح لا يُقبل بصمت.
- max الأصغر من أكبر قيمة يرفض أو يعيد التحجيم وفق عقد معلن.
- لا يتجاوز bubble نصف القطر المعلن.
- zero وunknown وnegative لا تختلط.

### W3.3 هندسة الرسم

- الحاوية تملك variant أو أبعادًا موثقة.
- labels والأرقام لا تتداخل.
- لا يصبح الرسم نحيفًا أو عريضًا بسبب رقم محلي في المعاينة.
- لا يغير المستهلك هندسة الرسم عبر override غير موثق.
- fallback البيانات، إن كان داخل المكوّن الحالي، يلتزم بقرار D-UI-04.

### W3.4 الألوان داخل الرسوم

- استخدم ألوان data الموجودة في التوكنز الحالية كما هي.
- لا تغير palette لمعالجة مشكلة هندسية.
- إذا ظهرت مشكلة contrast مثبتة، سجلها في التقرير النهائي مع القيم الدقيقة، ولا تنفذ تغييرًا لونيًا ضمن هذه الجولة.

### W3.5 ما لا يضاف

لا تضف ضمن إصلاح chart الحالي:

- filter product flow.
- sort workflow.
- pagination product behavior.
- zoom interaction.
- dashboard جديد.

إذا أثبتت كثافة البيانات أن هذه الوظائف ضرورية، تسجل كقرار منتج منفصل.

## Wave 4 — RTL وUI Locale وPreview Integrity

### W4.1 RTL/LTR

- الخصائص المنطقية للمسافات والمحاذاة والحدود.
- back/next والرموز الاتجاهية تعكس عند تغير المعنى فقط.
- الأرقام والمعرفات المختلطة لا تكسر المحاذاة.
- العربية واللاتينية الطويلة تختبران داخل نفس المكوّن.

### W4.2 Calendar وdate control

- يحافظ المكوّن على هويته البصرية الحالية.
- native date behavior لا يُعاد تصميمه كميزة جديدة.
- أي placeholder أو اختلاف منصة يسجل كـ`NOT PROVEN` أو قرار مالك، لا يُعالج بتغيير هوية المكوّن.

### W4.3 المعاينات

- المعاينة تعرض المكوّن الحالي كما هو، دون CSS خاص يخفي فشل المصدر.
- إذا كان هناك wrapper تجريبي يحتاج إصلاحًا، يفصل بوضوح عن عقد المكوّن.
- لا تُعدّل screenshot أو HTML generated بدل المصدر.

## 6. قالب إلزامي لكل Finding

يجب أن يكتب Zed AI لكل بند منفذ أو مؤجل:

```text
Finding ID:
Status: CONFIRMED / NOT REPRODUCED / OWNER DECISION / DEFERRED
Current source file and line range:
Current evidence:
Root cause:
Owning layer:
New UI contract:
Reference and classification:
Owner decision required: yes/no
Files changed:
Tests added or updated:
Failing evidence before:
Passing evidence after:
Viewport and direction:
Color tokens changed: none (must remain none)
Known non-goals:
```

لا يسمح بحقل `Color tokens changed` بأي قيمة غير `none` في هذه الجولة.

## 7. الاختبارات المطلوبة

### 7.1 اختبارات المصدر

- لا قيم صلبة غير مبررة.
- لا أسماء توكنز جديدة بلا عقد.
- لا selectors مكررة تخالف state contract.
- لا listeners مكررة بعد re-init.
- لا تغييرات ألوان مقارنة بـ`shared/tokens.css` baseline.

### 7.2 اختبارات المكونات

- default/pressed/focus/selected/disabled/busy/error/empty.
- نص عربي طويل.
- نص لاتيني طويل بلا مسافات حيث ينطبق.
- RTL/LTR.
- 320/360/390/430.
- layer open/close/focus restore.
- tab activation ثم الوصول إلى panel.
- chart data mutation وتحديث summary.
- zero/unknown/negative/invalid scale.

### 7.3 الاختبارات البصرية

- لا اختلاف غير مبرر بين component preview وstandalone preview.
- لا overflow أفقي غير مقصود.
- لا قص للرقم أو label أو icon.
- لا تكرار safe-area داخل التركيب.
- لا تغير في ألوان الهوية.
- لا تغيير في المقياس البصري بين المكونات المتشابهة.

### 7.4 حدود الدليل

نجاح Chromium أو probe آلي يثبت البيئة التي شُغّل فيها فقط. لا يعلن Zed AI أن المكوّن “جاهز لكل الأجهزة” من دون دليل مستقل. إذا لم تتوفر بيئة أخرى، يسجل `NOT RUN`.

## 8. بوابة القبول

لا يعتبر الإصلاح مكتملًا حتى:

1. يكون كل Finding نشط `CONFIRMED` قبل الإصلاح ثم `PASS` بعده أو موثقًا كـ`NOT REPRODUCED`.
2. لا توجد قرارات `OWNER DECISION` مخفية داخل الكود.
3. المكونات الحالية تبدو من نظام واحد وفق تصور UI البصري.
4. لا تغير الهوية أو قيم التوكنز اللونية.
5. لا توجد إضافات خارج UI الحالي.
6. كل إصلاح مرتبط بملف اختبار أو probe أو دليل مرئي.
7. التقرير النهائي يذكر ما لم يُختبر بدل ادعاء النجاح.
8. الفرع الوحيد يحتوي commits مفهومة، و`main` لم يُعدّل مباشرة.

## 9. تقرير Zed AI النهائي

يجب أن يسلّم Zed AI تقريرًا واحدًا داخل المستودع يتضمن:

- baseline SHA.
- اسم فرع الإصلاح.
- قائمة Findings النشطة وحالتها.
- الملفات المعدلة.
- العقود التي تغيرت.
- الاختبارات قبل وبعد.
- الأدلة البصرية والقياسات.
- البنود المؤجلة.
- قرارات المالك المطلوبة.
- أي `COLOR PROPOSAL — NOT IMPLEMENTED` مع القيم الدقيقة.
- تأكيد صريح أن ألوان الهوية لم تتغير.
- تأكيد صريح أنه لم يضف مكونات أو نطاقًا جديدًا.

## 10. الخلاصة التنفيذية

المطلوب من Zed AI ليس بناء نظام جديد من تخمينه. المطلوب هو إصلاح UI الحالي من الجذر حتى يصبح:

- معماريًا صحيحًا.
- ثابت المقياس.
- متناسقًا بين المكونات والمعاينات.
- قريبًا من جودة Android Native في الشكل والحالات والهندسة.
- محافظًا على الهوية والألوان الحالية.
- خاليًا من القيم المحلية غير المبررة.
- صادقًا في حالات البيانات والرسوم.
- قابلًا للمراجعة من خلال أدلة واختبارات.

أي شيء يتجاوز هذا العقد يخرج من الجولة، ويسجل كاقتراح أو قرار مالك، ولا ينفذ تلقائيًا.
