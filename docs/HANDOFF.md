# التسليم — دليل المالك والمستهلك

هذا الدليل يجمع الإرشاد النافذ للتسليم في وثيقة واحدة: ما تُسلّمه المكتبة، وكيف يستهلكها الفريق المستهلِك من المصدر، وحدود الملكية، وما يبقى على المالك، ودورة التعديل وإعادة البناء. فرع `main` هو المصدر الوحيد، ولا حاجة لقراءة سجلات فروع أو جولات قديمة لفهم المصدر أو استهلاكه.

## ما تُسلّمه المكتبة

- مصدر المكونات في `components/`، والتوكنز والقواعد المشتركة في `shared/`، والأصول المحلية في `assets/`، وأمثلة المكونات في `previews/`، والمعرض الأخير في `previews/ui-system-showcase/`، والمواصفات والقرارات في `docs/`.

المصدر القابل للتعديل هو التسليم الأساسي — عقد إلزامي:

- الصور والفيديو وملفات PDF أدلة معاينة فقط ولا تُقبل بدل المصدر، ولا تُستخدم صورة الكونسبت خلفية للمعاينة بدل بناء المكوّن (يسمح عرضها منفصلة كمرجع فقط).
- الصيغة: HTML/CSS/JavaScript واضح غير مصغر لمعاينات مكوّنات مستقلة، بلا مشروع تطبيق كامل ولا إطار بناء ثقيل — هذا اختيار لصيغة التسليم، لا قرار بتقنية تطبيق Micro — والمكوّنات منفصلة عن تنسيق لوحة عرضها.
- القيم المشتركة في `shared/tokens.css`؛ شكل المكوّن في `components/<family>/<family>.css` وسلوكه في ملف JS عند الحاجة؛ النصوص والحالات بيانات واضحة أو HTML دلالي، وليست نصوصًا مرسومة داخل الصور.
- الأيقونات SVG أو المصدر الرسمي القابل للتحرير؛ الخطوط ملفات أصلية مع التراخيص والمصادر، بلا روابط جلسة مؤقتة أو أصول مدفوعة غير متاحة. لا minified-only، ولا ملفات build وحدها، ولا لقطة شاشة داخل canvas بدل عناصر قابلة للتحرير.
- أي ملف تصميم إضافي يُسلَّم بصيغته الأصلية القابلة للتعديل؛ لا يُفرض على المستهلك أداة مدفوعة للوصول إلى المصدر الأساسي.
- لكل عائلة: `specification.md` (الغرض والأنواع والحالات والمقاسات وقواعد الاستخدام وRTL وحدود النطاق)، والمصدر الكامل مع معاينة تعرضه فعليًا، وREADME بأمر التشغيل والملفات المطلوبة ومواضع تعديل اللون/المقاس/النص/الأيقونة/الحالة، ومصادر الأصول في [`assets/SOURCES.md`](../assets/SOURCES.md)، ولقطات من المصدر المسلَّم نفسه بأسماء حالة/عرض واضحة.

## كيف يُستهلك المصدر

الاستهلاك من مصدر المستودع (`components/` و`shared/` و`assets/`)، لا من أرشيف ZIP ولا من `standalone.html` المولّد؛ الأخير ملف معاينة مولَّد وليس مسار استهلاك.

ترتيب التحميل:

1. `fonts.css` ثم `tokens.css` ثم `motion.css`.
2. CSS العائلات المستخدمة، ثم الوصفات الاختيارية: `access-gateway/welcome.css` و`compositions/mobile-shell.css`. لا تحمّل كل المكتبة دون حاجة.
3. القائمة: Navigation ثم AccountSettings. استعمل طبقة B07 مع `m-layer--drawer` و`data-account-initial-view="application"` و`data-account-to-account`؛ احتفظ بعناوين فريدة و`aria-labelledby` والغشاء والأزرار، وافصل العائلتين قبل إزالة الجذر.
4. سياق المنتج: Fields وNavigation وActionSheet وCarousel حسب الاستخدام، ثم `product-core` ثم `renderer`. استعمل `replace` و`destroy` وفق عقد المصدر، ولا تخترع `update`.

عقود نوعية:

- **Google-only:** التركيب القابل للاستهلاك موثق في [`google-welcome-usage.html`](../components/access-gateway/google-welcome-usage.html). يحمّل المضيف Google Identity Services ويرسم الزر الرسمي داخل `data-google-provider-slot`، ثم يدير credential callback والنتيجة والجلسة. `MicroAccessGateway.init(root, handlers)` خاص بالنموذج العام أو أزرار المزود المخصصة ولا يعيد بناء زر GIS. لا SDK أو OAuth في المصدر.
- **تراكيب Access Gateway الأربع:** `splash-usage.html` و`google-sign-in-usage.html` و`new-user-welcome-usage.html` و`returning-user-welcome-usage.html` مع `auth-screens.css` في [`components/access-gateway/`](../components/access-gateway/) — تراكيب UI قابلة للاستهلاك وليست صفحات مصادقة إنتاجية، ويبقى `google-welcome-usage.html` مثالًا مستقلًا لأدنى `m-welcome` و`m-session`. حمّل الخطوط والتوكنز أولًا ثم `buttons.css` و`auth-screens.css`؛ صفحات الترحيب تستخدم الأيقونة المحلية من `shared/icons.js`. يركّب المضيف شاشة واحدة حسب نتيجة موثوقة فقط، ويقدّم بيانات الحساب ويربط المتابعة/تبديل الحساب. لا يقرأ المكوّن البريد لتحديد حالة المستخدم ولا يخزن credentials أو session.
- **سياق المنتج:** الكتالوج يحدد الاعتماديات، ومواصفة العائلة تشرح التشريح والخصائص والحالات والاستخدام — راجع [`components/product-context/specification.md`](../components/product-context/specification.md) للسياق والصلاحية والبيانات وأحداث الطلب وإقرار النتيجة والتنظيف. الخيارات الأحدث اختيارية: `m-row--single`، وصفة B01، `attachmentSelection=append`، `conversationLayout=fill`، `action.emphasis=primary`؛ الافتراضات السابقة محفوظة. Figma لاحقًا يطابق هذه العقود ولا يصبح مصدرًا موازيًا مختلفًا.

هذه مكونات مشتركة: أنشئ غلافًا واحدًا لكل مكوّن ضمن stack المضيف، ولا تنسخ تفاصيل CSS وDOM إلى كل شاشة، ولا تنقل Showcase أو standalone أو صفحة المختبر كشاشات منتج. العقود التفصيلية في [API.md](../docs/API.md) والتراكيب في [COMPOSITIONS.md](../docs/COMPOSITIONS.md).

## حدود الملكية والتعارضات

- المضيف يملك: viewport-fit وPWA وtheme-color وشريط النظام ولوحة الهاتف وHistory/Back والمصادقة والبيانات والصلاحيات.
- حاضنة shell تملك الحواف في التدفق مرة واحدة؛ المتغيران `--micro-shell-inset-top/bottom` يقبلان `0px` عندما يملك المضيف الحافة خارجيًا. الحافتان الجانبيتان فيزيائيتان فلا تعكسهما RTL. اللوحة الثابتة تملك حوافها الخاصة؛ لا تجمع drawer وcenter. تذييل shell يمرر `--micro-inset-bottom: 0` لأبنائه لمنع تكرار الحافة.
- احتفظ بترتيب التحميل وأسماء الأصناف. ملفات `lab.css` و`login.js` و`tasks.js` مستهلكون تجريبيون وليست اعتمادات إنتاجية؛ لا مصادقة أو حفظ فيها. الخادم يفرض الصلاحيات والمكونات تعرضها فقط، ولا ينشئ Market أو Delivery أثرًا ماليًا تلقائيًا.
- عند التكامل لاحقًا: تحقق من stack المضيف وCSS العام والخطوط والطبقات والتمرير والجلسة والبيانات؛ مظهر التطبيق القديم ليس مرجعًا صحيحًا تلقائيًا. يمرر المضيف البيانات والصلاحيات ويؤكد التنفيذ، ولا يفسّر كلام المساعد ككود أو تفويض. اختيار الصور محلي ولا يحذف صورًا خادمية. `fill` يحتاج حاضنة ذات ارتفاع معلوم.
- الهوية والقياسات محفوظة: الشعار v2 والخطوط والتوكنز؛ شعار الترحيب 128×40 مع مساحة خلو 12؛ أهداف عناصر Micro 48 والحقول 52 والنص الأساسي 16/26؛ تباعد الوصفات من السلم الحالي. زر Google الرسمي يملؤه GIS، ويختار المضيف الحجم الأكبر المناسب للهاتف (يفضل 48px عندما يدعمه المزود، دون transform). ألوان Google الثلاثة تخص زر المزود حصريًا وتخضع لبوابة دقيقة وليست لوحة ألوان لـMicro؛ الإنتاج يستخدم زر مزود الهوية المدعوم ويتحقق من إرشاداته وترجماته السارية — أصل العلامة ومصدرها في [`assets/providers/README.md`](../assets/providers/README.md). دليل الحركة في [DESIGN-FOUNDATIONS.md](../docs/DESIGN-FOUNDATIONS.md). عرض اللوحة 80% مقترح للمعاينة وليس قرارًا نهائيًا.

## ما يبقى على المالك

- **التقبل البصري:** لا اعتماد بصري آلي. الحالات التي تعذّر فحصها تبقى NEEDS VISUAL CHECK، وأي بديل مؤقت يُسمّى صراحة ولا يُعد مطابقًا للهوية. نجاح فحوص Chromium ليس اختبار منصة ولا اعتمادًا بصريًا.
- **الاختبار على أجهزة حقيقية:** Samsung Galaxy S25/Chrome وTalkBack ولوحة النظام وWebKit واللمس الحقيقي وsafe areas وnative zoom ليست مختبرة آليًا — المصفوفة الكاملة في [TESTING.md](../docs/TESTING.md). لا ادعاء Native.
- **قرارات النضج:** النضج ملك الكتالوج ([`COMPONENT-CATALOG.json`](COMPONENT-CATALOG.json))؛ نقل العائلات والمتغيرات بين مستويات النضج قرار المالك، ولا ترقية تلقائية. علامتا `DRAFT FOR REVIEW` و`PROPOSED` حالتا عرض وليستا اعتمادًا إنتاجيًا.
- **قرار الدمج وبدء التكامل:** دمج أي عمل في `main` وبدء تكامل تطبيق Micro مسؤولية المالك؛ المكتبة لا تدمج نفسها ولا تبدأ التكامل. طريقة تشغيل التطبيق (Chrome/PWA) وعرض اللوحة ولمس شبكة الشهر قرارات مفتوحة. سجل القرارات والافتراضات والمؤجلات في [DECISIONS.md](../docs/DECISIONS.md)؛ عند تعارض قرارين يتقدم الأحدث ما لم يمس ثوابت الهوية.

## حدود النطاق والقرارات

- المكتبة جاهزة للاستهلاك البرمجي ضمن نطاق UI، وليست إعلانًا عن جاهزية تطبيق Micro أو UX أو المصادقة أو الحفظ أو النشر. التحقق الفعلي على Android/iOS وWebKit وقارئات الشاشة يحتاج مسارًا منفصلًا.
- لا backend أو AI أو OAuth أو حفظ إعدادات أو وجهات قانونية أو شخصية 3D داخل مستودع المكونات. مصادقة Google الفعلية والجلسة مسؤولية المضيف، وتسجيل Google مختلف عن استخدام Gemini.
- حصرية Google معتمدة للتركيب المستهدف: المستخدم الجديد والعائد يستخدمان إجراء Google نفسه، دون شاشة إنشاء حساب منفصلة.
- غياب الصورة في مثال Market حالة مقصودة؛ الصور الحقيقية تأتي من المضيف. الفراغ تحت مثال قصير لا يبرر حشو الشاشة بمعلومات أو زخارف.

## دورة التعديل وإعادة البناء

طريقة العمل في المستودع: اقرأ `AGENTS.md` ثم `DESIGN.md` و[STATUS.md](../docs/STATUS.md)؛ اختر مكونًا من [COMPONENT-INVENTORY.md](COMPONENT-INVENTORY.md) واقرأ مواصفته قبل تعديل المصدر. لا تعتبر المعرض شاشة منتج ولا تنقل fixtures إلى منطق أعمال.

إذا تغيّر مصدر المكوّن:

1. حدّث المواصفة إذا تغيّر العقد.
2. حدّث المثال القابل للتعديل عند الحاجة.
3. أعد بناء standalone إذا كان التغيير يخص المعرض.
4. شغّل الفحوص المرتبطة وسجّل حدودها.
5. راجع RTL والقياسات والنص الطويل والحالات الفارغة.

قواعد التصحيح والتسليم:

- التصحيح على الملفات نفسها مع حفظ تاريخ Git؛ سجّل تغييرًا موجزًا ولا تُعد إنشاء المكتبة من الصفر.
- التسليم عبر فرع وPR؛ النتيجة DRAFT حتى مراجعتها واعتمادها. إن لم توجد صلاحية كتابة، سلّم ZIP بالمصدر الكامل مع تقرير، دون ادعاء الرفع.
- إثبات قابلية التعديل: تحقق مرة واحدة أن تعديل توكن (مسافة أو انحناء) ينعكس على العينات التي تستخدمه، وأن تغيير النص والأيقونة متاح من المصدر؛ أعد القيم المعتمدة قبل التسليم ووثّق الخطوات والنتيجة دون إنشاء نسخة ثانية لكل تغيير.
- عند تعذّر قدرة أو أصل: سلّم ما استطعت كمصدر وصرّح بما لم تعمل عليه؛ لا تختلق صورًا أو نتائج.

الأوامر من جذر المستودع:

```bash
uv sync
uv run python tools/check-all.py             # كل بوابات الجودة + git diff --check
uv run python tools/check-all.py --quick     # البوابات الثابتة وبوابات البناء فقط
python3 tools/build-ui-system-showcase-standalone.py --check   # إعادة بناء standalone الحتمي والتحقق منها
```

مصفوفة الفحوص الآلية وحدودها موثقة في [TESTING.md](../docs/TESTING.md).
