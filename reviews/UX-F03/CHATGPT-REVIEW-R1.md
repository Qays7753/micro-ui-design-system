## الإصلاحات المطلوبة — F03-R1-01..08

### F03-R1-01 — النسخة الهاتفية تبدأ بتقرير تقني ولوحة اختبار

**الملفات:** `index.html` و`example.css` و`README.md` وأداة البناء عند الحاجة.

عند فتح standalone تظهر `.f03-head` بنص UX-F03، IBM Plex، HugeIcons، تحميل B، RTL، DRAFT FOR REVIEW واسم الملف، ثم قسم SIMULATION بفقراته وقوائمه وأزراره. تجميع القسم في عنصر منفصل داخل HTML لا يجعله خارج واجهة الهاتف. هذا يخالف طلب المالك الصريح لعينة تشبه الاستخدام الحقيقي، لا صفحة نصوص واختبارات. [لقطة الصفحة كاملة](independent/r1/default-phone-390.png).

**المطلوب:** الوضع الافتراضي للمصدر والملف الواحد يبدأ بمهمة العنصر نفسها، دون تقرير/عدادات/أدوات اختبار مرئية أو قابلة للتبويب. انقل تفاصيل التنفيذ إلى README أو وضع مراجعة اختياري مغلق افتراضيًا، من المصدر نفسه وبلا نسختين يدويتين. يمكن تعريفها بنموذج تجريبي بعبارة قصيرة دون إغراق. اختصر نصوص المستخدم أيضًا: «ملاحظة تركيبية قابلة للتعديل» و«النسخة المؤكدة محدثة» والشرح الداخلي في الحوار ليست محتوى مناسبًا لتجربة الاستخدام؛ أمثلة مناسبة «أضف ملاحظة» و«تم حفظ التعديلات» و«هل تريد تجاهل تعديلاتك؟». لا نسخ نصوص المنتج أو افتراض قواعد أعمال.

**دليل الإغلاق:** افتح الملف الافتراضي دون query/hash خاص؛ قس ظهور عناصر التقرير والمحاكاة وترتيب التبويب، والتقط الشاشة الأولى والصفحة كاملة. لا يكفي وصفها «خارج واجهة المثال».

### F03-R1-02 — سهم الفئة يخالف أصل HugeIcons

**الملفات:** الرموز في `index.html`/أداة تضمينها و`example.css`.

أصل `assets/icons/chevron-down.svg` يحمل `fill="none"` على SVG. النسخة inline نقلت المسار ولم تنقل هذه الخاصية إلى symbol أو المضيف. `.f03-cat__chevron` لا تضبط fill؛ القياس الفعلي للـuse = `rgb(0, 0, 0)`، والسهم يظهر مثلثًا ممتلئًا. [لقطة التعديل](independent/r1/edit-phone-390.png).

**المطلوب:** استعادة خصائص الأصل المعتمد دون تصميم سهم بديل، وحفظها في المصدر ثم إعادة توليد الملف الواحد. راجع بقية الرموز للتأكد من وراثة خصائص SVG لا المسارات وحدها. لا تعديل على ملفات أصول المكتبة.

**دليل الإغلاق:** fill المحسوب = none للسهم في المصدر والملف الواحد، مع مقارنة بصرية فعلية. مساحة SVG أو وجود symbol وحدهما لا يثبتان صحة رسم الأيقونة.

### F03-R1-03 — نتيجة القراءة تستعمل مصدر وقت التسوية

**الملف:** `mock-adapter.js`.

`readCategories()` لا يثبت snapshot في entry عند بدء الدعوة؛ `settle()` ينسخ source الحالي. التجربة: مصدر `{a,before}` → readId=1 معلق → setSource `{b,after}` → تسوية readId=1. النتيجة كانت `{b,after}`. هذا يعيد مشكلة عزل الطلبات التي صُححت في F02.

**المطلوب:** snapshot مستقل لعناصر مخطط F03 `{value,label}` عند بدء كل read، وتسوية الطلب من snapshot الخاص به. تغيير المصدر أو كائناته بعد الدعوة يؤثر في الدعوات التالية فقط. لا حاجة لاستنساخ عام عميق.

**دليل الإغلاق:** اختبار تغيير المصدر وتعديل خصائص عناصره بعد بدء الطلب؛ كل نتيجة تخص بيانات وقت دعوتها، بما في ذلك قراءتان متداخلتان.

### F03-R1-04 — مؤقت طلب قديم يحسم طلبًا أحدث

**الملف:** `mock-adapter.js`.

المؤقت الافتراضي يستدعي `settle(kind)` التي تصل إلى pending[kind] الحالي، لا entry الذي أنشأ المؤقت. عند readId=1 افتراضي، ثم readId=2 مسلح error قبل انتهاء 700ms: مؤقت الأول حسم الثاني، وبقي الأول غير محسوم. القياس: first=null/firstSettled=false، second={readId:2,outcome:error}/secondSettled=true. الإعلان عن overflow لا يمنع هذا الخلل.

**المطلوب:** اربط المؤقت والتسوية التلقائية بالطلب الأصلي وهويته. الطلب المتروك يُلغى بعقد صريح أو تُسلَّم نتيجته القديمة لفلتر المستهلك؛ لا يظل وعد معلقًا بصمت، ولا تُحسم الدعوة الجديدة بواسطة مؤقت قديم. احتفظ بالتسوية اليدوية للطلب المستهدف بعقد واضح، ومنع تكرار save/check كما هو.

**دليل الإغلاق:** auto read1 ثم armed read2 قبل انتهاء auto، والعكس؛ حسم كل وعد حسب سياسته، دون تسوية مبكرة للطلب المسلح. أضف مسار فتح/إغلاق/إعادة فتح المنتقي السريع نفسه.

### F03-R1-05 — رد منتقي مغلق يمس جلسة تعديل جديدة

**الملف:** `example.js`.

فلتر readId يقارن readSeq فقط، دون سياق فتح المنتقي/جلسة التعديل. التجربة: تعديل → read empty معلق → إغلاق المنتقي → رجوع clean → فتح التعديل مجددًا → تسوية الطلب القديم. قبل الرد كانت الفئة cat-a وdirty=false؛ بعده صارت null وdirty=true والمنتقي مغلق. هذا رد لم يعد يخص سياق المستخدم الحالي، ولو بقي آخر readId رقميًا.

**المطلوب:** اربط صلاحية الرد بسياق القراءة وجلسة التعديل، وأبطل الطلب عند مغادرة سياقه. لا تجعل الرد المغلق/القديم يغير الفئة أو الرسالة أو التركيز أو dirty في جلسة أحدث، بما في ذلك رفض Promise. لا تستخدم reload كإصلاح، ولا تعدل MicroPicker/B07 لإخفاء المشكلة. الفئة لا تُسقط إلا من نتيجة مؤكدة صالحة للسياق الحالي.

**دليل الإغلاق:** السيناريو المذكور على الصفحة نفسها، ثم قراءة جديدة صحيحة وحسمها؛ تجارب الرد/الرفض أثناء إغلاق المنتقي أو أثناء جلسة تعديل جديدة، والطلب الحالي يبقى قادرًا على الحسم.

### F03-R1-06 — كتابة النجاح في منطقة live معزولة

**الملف:** `example.js`.

`applySaved()` يكتب `#f03-view-note` قبل إغلاق اللوحة. MutationObserver سجل كتابة النص بينما ancestor inert=true واللوحة لم تُغلق. لم يحدث تحديث نص لاحق بعد إزالة inert. النص يصبح مرئيًا بعد الإغلاق، لكن ذلك لا يثبت إعلان الحدث بقارئ الشاشة. **لم نختبر قارئ شاشة فعليًا ولا نجزم بما سينطقه كل قارئ**؛ الخلل المثبت هو توقيت الكتابة خارج النطاق المتاح، مخالفًا سياسة توجيه قناة السياق.

**المطلوب:** حدّث القيم المؤكدة عند نجاحها، واحفظ رسالة النتيجة، ثم أظهر/اكتب إعلان النجاح مرة واحدة بعد `micro-navigation:closed` للوحة نفسها وإزالة عزل الخلفية. لا رسالة نجاح مكررة في سياقين، ولا سرقة تركيز إضافية، ولا فقد الرسالة مع reduced-motion/الإغلاق المتزامن.

**دليل الإغلاق:** سجل ترتيب إغلاق اللوحة/إزالة inert/كتابة الرسالة؛ الكتابة المعتمدة بعد تفعيل سياق العرض ومرة واحدة. ظهور النص أو role=status وحده لا يكفي. TalkBack/VoiceOver يبقيان NOT RUN حتى تجربة فعلية.

### F03-R1-07 — المحاكاة اليدوية تعلق المستخدم داخل عملية لا يستطيع حسمها

**الملفات:** تركيب/موصل/README وفق الحل المحدود المختار.

التجربة من الأزرار الفعلية: تسليح not-saved من SIMULATION → تعديل الاسم → حفظ. العملية تبقى saving والطلب pending؛ زر «إنهاء الحفظ» غير معطل لكنه داخل inert لأن اللوحة مفتوحة. مغادرة اللوحة محجوبة أثناء saving، ولا يستطيع مستخدم الهاتف إنهاء السيناريو دون console أو إعادة تحميل. نفس العزل يمنع حسم القراءة/التحقق يدويًا.

**المطلوب:** مع إخفاء أدوات الاختبار افتراضيًا (01)، اجعل وضع المراجعة اليدوي، إن أبقيته، مكتملًا وقابلًا للتشغيل على الهاتف دون console: مثل سيناريو محدد يُحسم داخل الموصل بوقت حتمي، أو تحكم فحص واضح داخل النطاق النشط في وضع المراجعة فقط. لا تعطل inert أو حصر التركيز أو حراسة المغادرة، ولا تضع أزرار debug في الوضع الافتراضي. إن قررت قصر الحالات المسلحة على الفحص البرمجي، احذف ادعاء القدرة على تشغيلها يدويًا والأزرار المضللة ووثق الحدود صراحة، مع بقاء تجربة الهاتف الافتراضية مكتملة.

**دليل الإغلاق:** دورة فشل/unknown/check/read من واجهة وضع المراجعة الفعلية إن وجد، بلا evaluate للإنهاء وبلا reload؛ أو إثبات إزالة واجهة التسليح اليدوية المضللة وتوثيق أن الحالات الخاصة آلية فقط. الفحص البرمجي الحالي ليس دليل استخدام يدوي.
