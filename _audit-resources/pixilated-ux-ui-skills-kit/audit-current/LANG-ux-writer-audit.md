# LANG — UX writing, Arabic, RTL and content-contract audit

**Scope:** Independent language/content audit of this UI system under construction. Micro is future context only; no other repository/app was opened or contacted, and no external URL was contacted. All people, names, measures and scenarios in reviewed examples are treated as fixture/demo content, not as real users, analytics or personas. No product, source, docs, preview, config or showcase file was edited.

## Result

- UX Writer skill: **LOADED + APPLIED** to all 14 listed component families, their variants/states and composition/showcase text. Four findings: **1 LIKELY, 3 CONFIRMED**.
- Overall copy quality is predominantly clear Modern Standard Arabic (MSA), with visible labels separated from helpers, meaningful icon-button names, Arabic examples and explicit demo disclaimers. That should not be mistaken for a complete reusable localization/content system.
- Priority is future-state readiness: define locale/string/number/plural contracts before this system is transferred; distinguish fixture copy from defaults that ship with a component; sanitize asynchronous errors before they become user-facing strings.
- No user research or analytics was available or inferred. This audit assesses implementation and copy quality only, not real-user comprehension.

## Findings (language/content)

### LANG-001 — Arabic strings and locale/format policy are component-local, not a system contract

- **Skill:** `ux-writer-agent` · **Category:** Localization/content architecture · **Severity:** Moderate · **Status:** **LIKELY**
- **Source:** `components/order-schedule/order-schedule.js:45–55, 126–140` (Arabic month/day arrays, manual count grammar, western-digit output); `components/order-schedule/specification.md:3, 81–83`; `components/info-strip/info-strip.js:47, 67–88`; `components/carousel/carousel.js:228–260, 280–291`; `components/selection/picker.js:247–258`; `components/access-gateway/access-gateway.js:107, 149–166, 186–234`. Relevant visible copy/ARIA is authored in component source and markup rather than through one evident catalog/locale input.
- **Evidence:** Multiple independent families hard-code Arabic labels and defaults; `order-schedule` explicitly documents Arabic/Gregorian/Western digits while other families concatenate numeric indices in Arabic or accept consumer-formatted values. `components/data/data.js:130–138` returns `String(v)` for numeric display unless `data-display` is supplied. The only audited tool extraction found 339 unique strings in the showcase HTML, not a translation catalog. This proves fragmentation, **not** that the system must support any particular additional language.
- **Root cause:** The library is Arabic-first, and message/value ownership is split ad hoc between literal JS defaults, example HTML and consumer-provided content. Locale scope, source-string ownership, formatting, and fallback behavior have not been expressed as a shared contract in the inspected material.
- **Impact:** A single phrase change or locale/digit policy can drift across visible copy, accessible names, live announcements, examples and generated fallback text. Future reuse outside the one documented Arabic calendar locale is harder to audit. No current user impact or translation failure is claimed.
- **Current patch:** None. No product files changed. Current workable boundary is to keep consumer-supplied content/data caller-owned and recognize embedded UI-state phrases as component-owned defaults.
- **Future State:** Decide whether Arabic MSA is the only shipped locale or the first locale. If Arabic-only, publish a centralized Arabic string/format contract and explicitly state western vs Eastern Arabic digits for each data type. If multi-locale, add a small locale/message adapter with stable string IDs for reusable UI states (e.g. `picker.search.empty`, `picker.load.error`, `carousel.position`, `orderSchedule.count`, `access.submit.error`), typed interpolation, plural selection and date/number format helpers. Keep data values/units and business outcomes caller-owned; don't infer customer-specific grammar from arbitrary text. Share the resolved message between visible text and ARIA/status announcement. Permit safe, complete consumer override; use a clear policy for missing keys rather than silently rendering internal keys.
- **Recommendation / size:** Structural content-contract work, not a mechanical replacement pass. First enumerate strings by ownership and default/fixture status, then centralize shared component state copy and formatting, then add locale tests. Do not localize everything based on fixture wording.
- **Risk:** A premature general-purpose localization framework can bloat a small library; dynamic Arabic grammar can be broken by naïve singular/plural interpolation; a broad move may accidentally change fixture copy or live-region timing.
- **Acceptance tests:** `ar` defaults render exactly the approved copy; override/missing-key behavior is explicit; Arabic plural cases 0/1/2/3/10/11/99/100 are tested; mixed Arabic/Latin identifiers and long Western/Eastern digit strings remain legible in visible and accessible names; date and number helpers cover documented boundaries; state changes announce the same resolved text once. Test 320/360/390/430 RTL and LTR only for the declared contracts; do not claim native zoom/screen-reader coverage without those tests.
- **Owner decision required:** Yes, before building localization infrastructure. **Question:** Is this reusable kit strictly Arabic MSA, or should it be locale-ready for English/other Arabic regional conventions at transfer? For each locale, which digit family is expected for dates, metrics and user-entered values? **Options/effects:** (A) Arabic-MSA/Western digits only—smallest API, but explicitly limits portability; (B) Arabic first, locale adapter from now—more upfront work, avoids rewriting core copy later; (C) fully localized catalog/formatting—most flexible, highest maintenance and unnecessary without a confirmed target. **Recommendation:** B, with Arabic MSA and Western digits as explicit current defaults while preserving caller-provided formatted values. Blocks central contract design; safe to defer actual non-Arabic strings.

### LANG-002 — Demo count copy needs review; a visible/accessible mismatch is confirmed at 4

- **Skill:** `ux-writer-agent` · **Category:** Arabic grammar / fixture consistency · **Severity:** Moderate · **Status:** **CONFIRMED**
- **Source:** `components/info-strip/example-usage.html:23–28`; `previews/info-strip/index.html:36–38`; `previews/ui-system-showcase/index.html:480–482, 495–497, 546–554`.
- **Selector/content:** `.m-info-card__number` plus `.m-info-card__unit`; authored accessible name on the same `<article>`.
- **Evidence:** The inspected `visual-info-strip-390.jpg` shows the card as `18 طلب`. The component example also pairs visible `18` + `طلب` and labels its card “عدد الطلبات”; the showcase uses `aria-label="طلبات اليوم، 18 طلب"`. In a standard MSA count phrase, `18 طلبًا` is the recommended fully inflected wording (the singular noun is accusative tamyīz, not nominative). Since the card visually splits number and unit and does not supply a complete clause, this audit does not treat that isolated `18 طلب` as a proven grammatical error; it recommends `18 طلبًا` when the intended reading is the count phrase. A separate showcase fixture has visible `4` + `طلب` while its accessible name says `4 طلبات`; this visible/accessible mismatch is certain, and `4 طلبات` is the standard count phrase for the intended reading.
- **Root cause:** Number, unit and accessible summary are manually maintained as separate strings; no fixture-level grammatical review catches mismatch.
- **Impact:** The confirmed `4` fixture can present different grammatical forms to sighted and screen-reader users. The `18` fixture has a clearer recommended full count phrase, but its current split-card syntax is not asserted as a confirmed defect. Because components accept arbitrary consumer copy, this must not be fixed by guessing at runtime.
- **Current patch:** None. Recommended fixture copy: author the `18` count phrase as `18 طلبًا` in visible and accessible text when that complete reading is intended; for the confirmed `4` mismatch use `4 طلبات` in both.
- **Future State:** Keep generic card API simple and semantically honest: consumer owns `label`, formatted `value`, `unit`/reading text and accessible summary. Provide optional documented formatter/example helper only where count semantics are known, not heuristic suffix changes. In fixtures, author the entire phrase from one source or derive the accessible label from the same finalized reading. Add a content review table of quantities used in all demo examples (0/1/2/3–10/11–99/100+) and label fixture values explicitly as examples.
- **Recommendation / size:** Immediate fixture-only patch is small; reusable Arabic count formatter and locale contract is structural and belongs under LANG-001.
- **Risk:** Changing a generic unit or introducing runtime agreement may corrupt currencies, measures or invariant labels; avoid assumptions about a noun's grammatical gender or whether an “unit” is a count noun.
- **Acceptance tests:** Every visible card's numeric phrase matches its `aria-label` semantically; reviewed Arabic fixtures use approved agreement for 0/1/2/3–10/11–99/100+ where applicable; arbitrary units remain literal; exact content in screenshots and accessibility tree matches.
- **Owner decision required:** Yes for whether Western digits and this MSA phrasing are the default fixture style; not required to confirm the `4` mismatch. **Question:** Approve `18 طلبًا` / `4 طلبات` as the complete count phrases in these fixtures? **Recommendation:** Yes. **Effect:** Improves the examples without changing component behavior; correction itself need not block unrelated work.

### LANG-003 — Rejected callback exception text is displayed verbatim as user-facing error copy

- **Skill:** `ux-writer-agent` · **Category:** Error messaging / content boundary · **Severity:** Major · **Status:** **CONFIRMED** (local dynamic path reproduced with a synthetic technical rejection; no real user or production error involved)
- **Source:** `components/access-gateway/access-gateway.js:149–151, 163–166, 230–234`; contract summarized in `components/access-gateway/specification.md:26–30`.
- **Selector/state:** `.m-access-gateway [data-access-status]` in recovery, provider and submit promise rejection handlers.
- **Evidence:** Each `.catch()` selects `error.message` when present and passes it straight to `setMessage()`, which writes it into a live status node using `textContent`. Dynamic reproduction: loaded `http://127.0.0.1:5000/previews/concepts/index.html#gateway`, reconfigured the root through the public `MicroAccessGateway.init` API with `onSubmit: () => Promise.reject(new Error("FixtureTransportError: E_DEMO_UNAVAILABLE"))`, and submitted only valid synthetic fixture values. The visible DOM status was exactly `FixtureTransportError: E_DEMO_UNAVAILABLE`; it had `role="status"`, `aria-live="polite"`, `data-tone="error"`, and occurred exactly once in both the status node and the gateway text. No external request was made. Cropped evidence: `generated-artifacts/pixilated-audit/LANG-003-synthetic-error-status-crop.png`. The separate `result.message` success/denial path is intentionally consumer-authored and is not this finding.
- **Root cause:** The implementation equates the Error object's technical `message` with reviewed localized user copy.
- **Impact:** A consumer rejection containing a technical `Error.message` is displayed verbatim in a DOM node exposed as a polite status live region. The synthetic local reproduction confirms this path, not an observed audible screen-reader announcement or real-user leak. Real integrations, users, network calls and production errors were not involved.
- **Current patch:** None. A safe default could be `تعذّر إكمال تسجيل الدخول. حاول مرة أخرى.` for submission, `تعذّر تنفيذ الدخول. حاول مرة أخرى.` for a provider, and `تعذّر إرسال طلب المساعدة. حاول مرة أخرى.` for recovery; keep raw error out of visible copy.
- **Future State:** Separate failure presentation from diagnostics. Let the consumer provide an explicitly user-facing localized message or map an error kind to a safe message; otherwise show a neutral, actionable fallback. Emit/report the exception through an intentionally private consumer callback only if the API requires it, without putting stack, credentials, response bodies or arbitrary error details into DOM/live regions. Preserve current `result.message` only as a named, documented user-facing field, not a generic exception message.
- **Recommendation / size:** Patch-sized error-boundary improvement plus a small contract/API definition; do not attempt to translate or sanitize arbitrary technical prose automatically.
- **Risk:** Too-generic fallback can hide an actionable cause; diagnostic forwarding can create a separate privacy issue if it includes credentials. `result.message` override and outcome semantics must remain predictable.
- **Acceptance tests:** Reject with synthetic HTTP/code, English, long and empty errors; visible and live-region copy remains approved localized and actionable; consumer-supplied safe message appears as documented; no error object/credentials appear in the UI or event detail; error state is announced once.
- **Owner decision required:** Yes for whether `result.message` is guaranteed user-facing and for diagnostic callback ownership. **Question:** Should the library accept an explicit `userMessage`/error mapper and otherwise use neutral Arabic copy, rather than exposing `error.message`? **Recommendation:** Yes. Blocks final callback content contract; does not block unrelated component work.

### LANG-004 — Picker's generic loading, empty and error defaults do not name the result context

- **Skill:** `ux-writer-agent` · **Category:** State microcopy / clarity · **Severity:** Minor · **Status:** **CONFIRMED**
- **Source:** `components/selection/picker.js:106–110, 126–148, 247–259`; picker state contract in `components/selection/specification.md:25–30`.
- **Selector/state:** `[data-picker-search]`, generated `.m-picker__state`, `[data-picker-retry]`, `[data-picker-summary]`.
- **Evidence:** True data `empty` defaults to `لا نتائج`; `error` defaults to `تعذر القراءة`; `loading` defaults to `جارٍ القراءة…`. Search-no-match is separately more explicit at line 109: `لا نتائج مطابقة — جرّب اسمًا آخر`. Status callers may override `msg`, but default `empty`/`error` do not state that options/results failed to load.
- **Root cause:** The fallback message labels describe an operation/state generically rather than naming the entity/results; the user-facing search state already demonstrates a more specific pattern.
- **Impact:** “لا نتائج” can be read as either no available data or no search match, and “تعذر القراءة” is vague. The existing retry button supplies an action but doesn't clarify what failed.
- **Current patch:** None. Suggested default deck: loading `جارٍ تحميل الخيارات…`; true empty `لا توجد خيارات متاحة.`; no match `لا توجد نتائج مطابقة. غيّر عبارة البحث أو امسحها.`; error `تعذّر تحميل الخيارات.` alongside `إعادة المحاولة`.
- **Future State:** Maintain distinct templates for not-yet-populated data, a successful search with zero matches, and failed loading. Use caller-supplied entity noun only as a safe plain-text interpolation with locale-appropriate grammar. Keep a retry CTA verb phrase aligned with retry semantics; add context/action without inventing a cause when unknown.
- **Recommendation / size:** Patch-sized default-copy improvement. Message catalog ownership can align with LANG-001.
- **Risk:** The picker can serve different entity types, and “options” may not be consumer terminology. Keep override available and avoid naming a specific business object in generic code.
- **Acceptance tests:** Tests assert separate text for ready+no search matches, loaded-but-empty data, loading and read failure; override text remains literal and safe; retry button is present only for error; all visible and accessible status text is localized consistently and remains understandable when wrapped at 320px RTL.
- **Owner decision required:** Yes for generic noun and whether empty-data default should have a first-use CTA owned by consumer. **Question:** Use neutral generic “options” or require consumer-provided subject copy? **Recommendation:** Keep a generic `options` fallback and allow complete `msg` override; do not add a business-specific CTA to the picker. Blocks wording approval only.

## Content contract proposed for Future State

1. **Separate content ownership:** component-owned UI-state strings vs consumer-owned domain labels/units/outcomes vs fixture-only showcase prose. Mark fixture values as demonstrative; never infer domain grammar or semantics from them.
2. **Give reusable strings stable contextual IDs:** e.g. `selection.picker.loading`, `selection.picker.empty`, `selection.picker.noResults`, `selection.picker.error`, `navigation.carousel.position`, `fields.clear.label`, `access.submit.invalidEmail`. One resolved copy value must feed both visible output and associated ARIA/live announcement.
3. **Use explicit parameters and locale-aware grammar:** count phrases require exact number + grammatical form; dates/times/numbers use one reviewed locale formatter; support safe text interpolation only. Don't concatenate fragments that can reorder in RTL.
4. **Preserve bidi boundaries:** numeric/text mixed runs, counts, identifiers, email and currency should have deliberate `dir`/`bdi` isolation in visual and accessible output. Preserve consumer-formatted values rather than silently replacing their digit family.
5. **Errors should be useful, calm and safe:** say what failed, next action when known, don't blame, and don't present internal codes. Generic components cannot invent causes; callers supply contextual safe copy.
6. **Define voice after owner decision:** current examples trend clear, direct MSA with a few conversational imperatives (“جرّب”). No dialect or future product personality should be inferred from fixtures. Recommend neutral professional MSA, active verbs, sentence-case punctuation, concise labels and action-oriented errors.
7. **Keep strings flexible in layout:** accept Arabic expansion and long caller text; no fixed-length truncation. For fixed-height/narrow status surfaces, test long Arabic names, unbreakable mixed identifiers and dates at 320/360/390/430 RTL. A screenshot showing clean wrapping is evidence only for that exact sample/state.
