## واجهة الموصل التجريبي (قابلة للاستبدال)

`mock-adapter.js` يوفر `F03Sim.createConnector({categories})` — واجهة محلية مقترحة للعينة، **ليست API جديدة للمكتبة**:

```js
save({ attemptId, values })            // → Promise<{attemptId, outcome: 'saved'|'not-saved'|'unknown'}>
check({ attemptId })                   // → Promise بالصيغة نفسها — استعلام للمحاولة نفسها بلا حفظ جديد
readCategories({ readId })             // → Promise<{readId, outcome: 'ready'|'empty'|'error', items: [{value,label}]}>
```

- **الوضع الافتراضي حتمي وينجح تلقائيًا**: بلا سيناريو مسلّح تُحسم كل دعوة تلقائيًا بعد **700ms ثابتة** (`F03Sim.AUTO_SETTLE_MS`) بالنتيجة الافتراضية (`saved`/`saved`/`ready` بالفئات) — المسار الافتراضي للمستخدم يعمل بسهولة وينجح. هذا زمن خدمة المحاكاة داخل الموصل، **لا مؤقت واجهة يقرر نجاحًا**: الواجهة تنتظر Promise المستهلك دائمًا، ولا نجاح قبل نتيجة مؤكدة.
- **السيناريو المسلح** يطبق على الدعوة المقبلة فقط ويجعلها معلقة حتى أمر `settle(kind)` الصريح — بلا sleeps واجهة. رفض Promise أثناء save يعامل unknown إن لم يؤكد العقد عدم الحفظ؛ رفض check يبقى unknown؛ ولرفض معلوم صريح استخدم `not-saved`.
- **رد بمعرف قديم**: لا توجد أداة تسوِّي Promise الطلب المعلق (كانت تستهلكه وتعلق المحاكاة — درس F01-R1-05). التسليم عبر `F03Example.deliverTestResponse(kind, payload)` الذي يستدعي معالِج النتائج نفسه لدى المستهلك (نفس فلتر attemptId/readId) **دون استهلاك الطلب المعلق**؛ فيُتجاهل الرد ويتاح إنهاء الطلب بنتيجته الصحيحة بعده. أزرار «استجابة بمعرف قديم» في لوحة SIMULATION تستخدم هذا المسار.
  - **ما يثبته وما لا يثبته**: يثبت فلتر المستهلك وتجاهله الكامل (قيم/رسالة/تركيز) واستمرار حسم الطلب الصحيح بلا إعادة تحميل أو حفظ جديد. **لا يثبت** وصولًا شبكيًا فعليًا لرد طلب سابق — حد موثق لا يُدّعى.
- `setSource(items)` لتبديل مصدر الفئات (للفحص: اختبار empty وسقوط القيمة).
- العدادات (`save/check/read`) وسجل الدعوات للفحص فقط — لا تدخل رسائل المستفيد.

## تركيب الشاشات وقرارات المستهلك

- **منظر عرض واحد** للنسخة المؤكدة فقط + فعل أساسي واحد «تعديل». لا لوحة مؤشرات ولا صفحات تسويقية ولا قائمة مكونات.
- **نموذج التعديل «الصغير» لوحة سفلية B07** — هذا هو «نموذج كامل داخل modal وحراسة مغادرته» المؤجل صراحة من قرار F01 بعد مراجعة R1 (UX-COMPONENT-MAP) إلى تطبيق لاحق، وهو ما تختبره F03:
  - «رجوع» وزر الإغلاق الظاهر في الرأس **بلا `[data-layer-close]` الجاهزة** كي يمرا عبر حراسة المستهلك `requestLeave()` — لا تغيير على عقد B07.
  - الضغط بالخلفية `data-backdrop="keep"` (بقاء ضمني — لا مسار تخلي غير معلن).
  - **Escape**: مستهلك العينة يسجل مستمع `keydown` بطور الالتقاط على المستند يسبق مستمع B07 ويوجه الحدث دون تعديل core: طبقة أعلى مفتوحة (منتقي/حوار) → يُمرَّر إلى B07؛ dirty → يفتح حوار البقاء/التخلي (UX-17: لا Escape صامت للتخلي)؛ pending → حجب برسالة موجزة؛ نظيف → يُمرَّر إلى B07 (إغلاق عادي واستعادة تركيز المشغّل). هدف استرجاع التركيز عند حوار Escape هو «رجوع» (موثق).
  - مغادرة أثناء saving/checking/unknown: محجوبة برسالة محلية موجزة — لا حوار تخلي ولا وهم إلغاء عملية جارية.
- **منتقي الفئة**: طبقة B07 ثانية تُركَّب فوق لوحة التعديل (z-index مضبوط بمستوى العينة في `example.css` — قرار تركيب لا قيمة بصرية) وتحتوي **المنتقي المعتمد** `MicroPicker` بعقده كما هي: قراءة بمعرف جديد لكل فتح، loading/error/empty تخفي الخيارات القديمة، البحث لا يلغي الحالة ولا يزيل صفها، «لا نتائج مطابقة» نتيجة تصفية بحث فقط، بذرة فئة اللوحة الجارية داخل المنتقي عند الفتح، اختيار فوري يغلق الطبقة ويعيد التركيز إلى صف الفئة. رسالة زوال الفئة (`empty` مؤكدة أو سقوط القيمة) ظاهرة داخل الطبقة بنمط B06 (`m-note--warning` + `role=alert`) وهي القناة الوحيدة لهذا الحدث (درس F02-R2-01)، وتُمسح باختيار جديد/قراءة جديدة/إغلاق. empty المؤكدة تُسقط فئة اللوحة الجارية (لا بديل تلقائي — نمط F02-R1-02) وتُلزم باختيار عند الحفظ.
- **حوار التغييرات غير المحفوظة**: حوار B07 موسط بنمط F01 — البقاء/Escape/الإغلاق الظاهر/الخلفية كلها بقاء؛ التخلي وحده يستعيد النسخة المؤكدة ثم يغادر اللوحة بعد اكتمال إغلاق الحوار، بلا أي حفظ.
- **بعد نجاح مؤكد**: اللوحة تُغلق وتعود العرض المحدَّث مع رسالة نجاح واحدة — دورة المهمة تكتمل (تعديل → حفظ → عرض محدَّث).

## الحالة والرسائل

محاور مستقلة: `dirty` (اختلاف القيم الخام عن المؤكدة، والعودة للأصل تعيد clean دون حفظ) و`invalid` (الاسم/الفئة) وحالة العملية: `idle | saving | failed | unknown | checking | saved`.

- **قناة واحدة لكل سياق (حدث = قناة واحدة)**: أثناء فتح اللوحة، رسالة العملية ملاحظة B06 ثابتة `role=status` داخلها — بلا `MicroMessages.announce` لنصها. بعد النجاح وإغلاق اللوحة، قناة سياق العرض (`role=status`) هي المالكة (نمط توجيه F02-R2-01 بين داخل الطبقة وخارجها). خطأ الاسم عبر `aria-describedby`/`aria-invalid` في رسالة الحقل؛ خطأ الفئة عبر رسالة صف الفئة المرتبطة `aria-describedby`. قناة القراءة داخل طبقة المنتقي live-only مخفية بصريًا (نمط F02) والحالة المرئية صف حالة المنتقي من core. لا Toast في F03 ولا لون نجاح لكل حقل ممتلئ.
- رسائل انتهى سببها تزال عند تغير القيم (درس F01-R1-03)؛ `failed` يبقى سجل محاولة دون عرضها كرفض للقيم الحالية؛ رسالة نجاح العرض تُمسح عند فتح تعديل جديد.
- أثناء saving/unknown/checking: الحقول **readOnly** (القراءة والنسخ محفوظتان، ليست fieldset معطلة) وزر الفئة معطل (لا تغيير فئة قبل حسم النتيجة)؛ busy على زر الحفظ فقط أثناء saving وزر التحقق فقط أثناء checking عبر `MicroButtons.setLoading` بتحميل B الافتراضي. زر «التحقق من النتيجة» يظهر ظهورًا فعليًا في unknown/checking فقط بقاعدة عينة `#f03-check[hidden]{display:none}` (درس F01-R1-01 — قاعدة عرض B01 تغلب إخفاء المتصفح).
- تركيز: فتح التعديل → الاسم (`data-autofocus`)؛ فتح المنتقي → حقل بحثه؛ حوار البقاء → زر البقاء؛ خطأ إدخال → موضع التصحيح؛ إخفاء زر تحقق مركز → زر الحفظ قبل الإخفاء (درس F01-R1-02)؛ إغلاق اللوحة/الحوار → يديره B07 (المشغّل أو أول عنصر صالح في الطبقة العليا)؛ بعد نجاح → مشغّل «تعديل».
- الحفظ تجريبي داخل الجلسة: لا localStorage ولا شبكة ولا مصادقة؛ لا يُدّعى حفظ إنتاجي أو تخزين دائم. البيانات تركيبية.
