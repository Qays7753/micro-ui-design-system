# التسليم الكامل لقائد Micro UI

**الحالة:** HANDOFF / مرجع استمرارية  
**آخر تحديث:** 2026-09-28 — Asia/Amman  
**المستودع:** `Qays7753/micro-ui-design-system` (عام)

## 1. لماذا هذا المشروع موجود؟

Micro تطبيق هاتف لإدارة مشروع صغير وعملياته. لا تنظر إليه كنظام مالي فقط: يشمل الطلبات، العمل، التوصيل أو جلب الطلبات، العلاقات مع الموردين والسوق، التتبع، الأدوات، والمالية. يحتاج صاحب المشروع إلى overview ذكي في الرئيسية، لكن مكتبة UI لا تحدد الآن محتوى الشاشة أو منطقها.

المشروع الحالي لا يبني شاشات Micro. هو يبني لغة UI وأدوات تركيب مستقلة يستطيع أي وكيل لاحق استخدامها لتطوير النظام من دون إعادة اختراع الشكل في كل مرة.

## 2. الهدف المتفق عليه

إنتاج concept system متكامل يتضمن:

- أسس الألوان والخط والمسافات والانحناءات والعمق والأيقونات.
- مكوّنات قابلة لإعادة الاستخدام وحالاتها الحقيقية.
- قواعد تركيب واستخدام تمنع الشكل الجاهز أو العشوائي.
- معالجة بصرية بترولية مميزة لكنها هادئة وقابلة للتعديل.
- مصادر HTML/CSS/JS/SVG واضحة وغير مصغرة، مع أمثلة مستقلة وأدلة مراجعة.
- SOP يسمح لوكيل آخر بإضافة نوع أو تعديل token أو تركيب المكونات بصورة متسقة.

خارج النطاق حاليًا:

- تصميم شاشات مكتملة أو journeys.
- تغيير منطق الأعمال أو البيانات أو user flow.
- إصلاح النصوص التعليمية الحالية أو كتابة محتوى نهائي لكل خدمة.
- ربط المكتبة بمنتج Micro الإنتاجي.
- اعتبار واجهة Micro الحالية مرجعًا يجب الحفاظ عليه.

## 3. الذوق والاتجاه البصري

الإحساس المطلوب: هادئ، احترافي، معاصر، دافئ قليلًا، ومصمم خصيصًا لا قالبًا جاهزًا. المظهر فاتح؛ البترولي هوية قوية، والنعناعي/الأبيض الدافئ أرضية هادئة، والمشمشي accent محدود. العمق خفيف، والانحناءات ناعمة، والبيانات واضحة.

الصفحة هي الوحدة الأساسية. نفصل الأقسام بالمسافة والمحاذاة والعنوان أولًا، ثم نستخدم سطحًا أو بطاقة فقط إذا احتاج المحتوى استقلالًا حقيقيًا. يجب ألا يبدو النظام «مجموعة بطاقات» ولا dashboard مولدًا بالذكاء الاصطناعي.

الأسطح البترولية البارزة يمكن أن تتضمن موجات أو إضاءة خافتة قابلة للتعديل، لا خلفية جامدة دائمًا، لكن المؤثر محصور في المواضع البارزة ولا ينتقل إلى القوائم والحقول وكل الأزرار. لا glassmorphism شامل ولا ضباب أو لمعان مستمر.

## 4. ثوابت المنتج البصري

- هاتف فقط الآن، مع استعداد Android وiOS.
- العربية RTL، والأرقام 0–9.
- الوضع الفاتح فقط في هذه المرحلة.
- IBM Plex Sans Arabic للعربية وIBM Plex Sans للأرقام واللاتيني.
- HugeIcons Stroke Rounded؛ لا خلط عائلات ولا Emoji بديلًا للأيقونة.
- هدف لمس 48×48px كقاعدة محافظة للمشروع.
- دعم 320/360/390/430 CSS px، والنص الطويل والتكبير حتى 200% ضمن حدود ما يمكن فحصه.
- لا hover شرطًا للاستخدام، مع `prefers-reduced-motion`.
- اللون لا يحمل المعنى وحده، والقيمة المجهولة ليست صفرًا.

القيم التفصيلية مصدرها `docs/foundations/Micro-UI-Foundations-V1.md` و`docs/SHARED-SPEC.md` و`shared/tokens.css` على فرع التنفيذ.

## 7. ما الذي كان آخر نقاش قبل نقل الدور؟

كان العمل سيتوسع لاحقًا إلى مكوّن carousel/stack لعرض عناصر أو بطاقات في الرئيسية مستوحى من فيديو مرجعي، مع إمكانية رؤية البطاقة التالية والإحساس بالحركة بين العناصر. لم يُعتمد مكوّنه ولم يُرفع الفيديو بعد إلى المستودع العام عند إعداد هذا الهاندوفر. لا تبدأ تنفيذه من الذاكرة؛ يحتاج brief مستقل يحدد الغرض والحالات والحركة وإتاحة reduced-motion والمصدر القابل للتعديل.

كما طُرحت الحاجة إلى تحويل مشاكل UI الحالية إلى معايير دولية وأفضل ممارسات بدل نسخ المشاكل إلى المكتبة. هذه المرحلة لم تُنفذ بعد، ويجب أن تتم في مساحة خاصة لأن الأدلة تتضمن لقطات من النظام الحالي.

## 8. جدار الفصل بين UI الجديد والنظام الحالي

هذه قاعدة حاكمة:

1. لقطة Micro الحالية دليل تشخيص فقط، وليست مرجعًا بصريًا.
2. لا تُرسل اللقطات أو تقرير العيوب الخام إلى وكيل التنفيذ.
3. قائد UI يستخرج منها قاعدة عامة محايدة قابلة للتحقق.
4. القاعدة تُراجع مقابل WCAG 2.2 وMaterial Design وApple HIG والمبادئ المعتمدة للمشروع عند الصلة.
5. ما يصل إلى Z AI هو المعيار الصحيح ومثال قبول/رفض عام، لا صورة الواجهة القديمة ولا اسم الشاشة ولا بياناتها.

المشكلات التي ظهرت في الصور الحالية — للاستخدام كفئات بحث لا كحلول جاهزة — تشمل كثافة النصوص التعليمية، ضعف التسلسل البصري، الإفراط في البطاقات والحاويات، عدم اتساق الألوان والأزرار والمسافات، تزاحم المعلومات والإجراءات، أحجام/أوزان طباعية غير منضبطة، وفصل ضعيف بين التنقل والمحتوى. التحليل الدقيق والأدلة يجب أن يبقيا خارج هذا المستودع العام.

## 9. نموذج التعاون

### قيس

- يحدد الهدف والأولوية.
- يراجع المقارنات البصرية المختصرة.
- يعتمد أو يرفض القرارات المقترحة.

### قائد UI الجديد

- يحافظ على الاتجاه والثوابت.
- يحدد النطاق ومعايير القبول.
- يكتب prompt دقيقًا للمنفّذ.
- يراجع المصدر والشكل والسلوك والأدلة.
- يحول العيوب القديمة إلى معايير آمنة.
- يمنع انتقال UX أو منطق الأعمال إلى مكتبة UI دون قرار.

### Z AI Flash

- ينفذ فقط التكليف المحدد.
- يعدل المصادر القائمة ولا يعيد البداية.
- يسلّم المصدر القابل للتعديل، الأمثلة، التوثيق، الفحوص واللقطات.
- لا يعتمد نفسه ولا يدمج ولا يغيّر نطاق المنتج.

## 10. عقد التسليم لأي دفعة قادمة

يلزم دائمًا:

- `specification.md` للغرض والأنواع والحالات والخصائص وRTL والاستخدام والموانع.
- CSS/JS/SVG/HTML كامل وغير مصغر، منفصل عن `board.css`.
- مثال مستقل يعمل خارج لوحة العرض.
- README يوضح التشغيل وأماكن تعديل اللون والمقاس والنص والأيقونة والحالة والبيانات.
- أصول محلية وتراخيص ومصادر.
- تقرير مراجعة يذكر commit المصدر، ما فُحص، وما لم يُفحص.
- لقطات من المصدر نفسه، لا صور مولدة كإثبات تنفيذ.
- تحقق من التوكنز، النص الطويل، المقاسات، RTL، التركيز، الحركة، التباين، والحالات المتزامنة ذات الصلة.

الفحص الآلي لا يغني عن مراجعة بصرية. Chromium headless لا يساوي اختبار Android/iOS أو قارئ شاشة أو لمس حقيقي؛ اذكر الحدود بصدق.

## 11. المخاطر التي يجب منعها

- شكل يشبه template أو AI dashboard: بطاقات متكررة، gradients عشوائية، ظلال موحدة، ومساحات غير منطقية.
- جعل النظام ماليًا بصريًا ومفاهيميًا على حساب العمليات والطلبات والموردين.
- تصميم شاشات كاملة داخل مهمة مكوّن.
- اختراع workflow أو حسابات أو أسماء تبويبات باعتبارها قرارات UI.
- استخدام ألوان البيانات في الأزرار والحقول للزينة.
- تقليد الواجهة الحالية أو المراجع حرفيًا.
- قبول صورة أو فيديو أو build من دون المصدر القابل للتعديل.
- اعتبار نجاح سكربت أو أرقام فحص بديلًا عن جودة الشكل.
- دمج PRs المتسلسلة بترتيب خاطئ أو مراجعة SHA غير الرأس الفعلي.

## 12. خريطة العمل التالية بعد الاستلام

1. **تثبيت الحالة:** افحص PR #1 و#2، المراجعات، والرؤوس الحالية.
2. **إغلاق الجودة:** راجع الإصلاحات المعلنة بصريًا وتقنيًا وسجل المتبقي فقط.
3. **قرار المالك:** اعرض المرشحات البصرية القليلة في مقارنة واضحة ولا تحولها إلى اعتماد صامت.
4. **تنظيم الأدلة الخاصة:** أنشئ مستودعًا خاصًا منفصلًا لصور Micro الحالية وتحليلها، إذا وافق المالك ووفّر الوصول.
5. **تحويل العيوب إلى معايير:** اكتب `CURRENT-UI-FINDINGS.md` الخاص ثم `FINDINGS-TO-STANDARDS.md`، وأرسل للمنفذ المعايير العامة فقط.
6. **الأصول المرجعية الآمنة:** افهرس الصور المفهومية التي أنشأها القائد والفيديو المرجعي مع وصف «ما الذي نتعلمه/ما الذي لا ننسخه».
7. **المكوّن التالي:** اكتب brief مستقل للـcarousel/stack أو أي أولوية يحددها قيس، ثم كلف Z AI Flash.
8. **الـSOP النهائي:** حدّث قواعد التركيب والتوسعة بعد اعتماد المكونات، قبل بدء تركيبها في Micro.

## 13. تعريف النجاح

ننجح عندما يستطيع وكيل جديد بناء أو تعديل مكوّن من دون سؤال عن الأسلوب من الصفر، ومن دون رؤية واجهة Micro القديمة، وتبقى النتيجة متسقة، قابلة للتعديل، قابلة للمراجعة، ولا تدّعي اعتمادًا لم يمنحه قيس.
